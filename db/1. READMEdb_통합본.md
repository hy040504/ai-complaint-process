# DB 스키마 설명 (통합본)

## 1. 한눈에 보기

- 스키마 : DB 안에서 테이블을 종류별로 나누어 담는 단위
- DB 1개 안에 스키마 2개
  - `complaint_rag` : AI가 검색하는 자료 보관
  - `complaint_app` : 민원 게시판이 쓰는 데이터 보관
- 두 스키마의 연결 : 단 1곳 (부서 번호)
- 테이블 수 : `complaint_rag` 7개, `complaint_app` 8개

## 2. 스키마가 2개인 이유

- 역할이 서로 다름
  - 검색 자료 : 원본 FAQ, 과거 사례를 적재한 데이터, 읽기 중심
  - 민원 데이터 : 시민과 담당자가 계속 쓰고 고치는 데이터, 쓰기 중심
- 민원 글이 검색 자료에 섞이지 않게 분리
- 검색 자료를 다시 적재해도 민원 데이터는 그대로 유지
- `complaint_app`만 지우고 다시 만들 수 있어 시연 준비 쉬움

## 3. complaint_rag (검색용)

- 역할 : AI가 답을 찾을 때 참고하는 자료 보관
- 우리 작업에서는 읽기만 하고 수정하지 않음
- 테이블 7개
  - `faq_knowledge` : FAQ 안내 자료 (94건)
  - `routing_cases` : 과거 민원 사례와 처리 부서 (5,015건)
  - `department_directory` : 부서 목록 (127개)
  - `index_metadata` : 색인 정보
  - `term_postings`, `term_statistics`, `corpus_statistics` : 키워드 검색용 통계 3개
- FAQ와 사례에는 비슷한 글을 찾기 위한 벡터(1024차원) 저장

## 4. complaint_app (민원 게시판용)

- 역할 : 시연 웹에 보이는 민원, 답변, AI 작업 기록, 담당자 처리 이력 보관
- 상태 : 이번에 새로 만드는 스키마 (`02_complaint_app.sql`)
- 테이블 8개
  - `users` : 사용자 (시민, 담당자)
  - `complaints` : 민원 한 건 (처리 기한 `due_at` 포함)
  - `messages` : 민원에 달린 답변, 추가 문의 묶음
  - `message_versions` : 답변 글의 버전
  - `ai_jobs` : AI가 일한 기록
  - `ai_results` : AI가 낸 결과 (신뢰도 `confidence` 포함, AI가 계산한 값을 저장만 함)
  - `job_events` : AI 작업 중 생긴 일
  - `complaint_events` : 담당자가 한 일(처리 이력)과 원문 열람 감사 기록

### 화면 기능과 테이블 연결

- AI 작성 / 담당자 수정 답변 구분 : `message_versions`의 작성 주체 칸
- 답변 수정 기록 보기 : `message_versions`에 버전별로 누적
- AI 작업 진행 상태 보기 : `ai_jobs`의 상태, 단계와 `job_events`
- 기한 관리 (D-day) : `complaints.due_at`에서 남은 일수를 계산
- 담당자 처리 이력, 진행 로그 : `complaint_events`
- 협조 요청, 기한 연장, 반려 기록 : `complaint_events`의 `kind`
- 원문 열람 감사 로그 : `complaint_events`의 `kind`가 `원문열람`인 줄

### complaint_events 설명

- 한 일의 종류(`kind`) 8가지 : 배정, 열람, 계획, 조치, 협조요청, 기한연장, 반려, 원문열람
- 한 사람(`actor_id`) : 담당자. 시스템이 한 일이면 비어 있음(NULL)
- 공개 구분(`vis`) 2가지 : `pub`(시민에게 보임), `int`(내부 전용)
- 한 번 쌓은 줄은 고치지 않고, 시간 순서(`at`, `id`)로 읽음
- `job_events`와 구분 : `job_events`는 AI 작업 기록 전용, `complaint_events`는 사람이 한 일 전용

## 5. 두 스키마의 연결

- 연결 위치 : `ai_results.department_id` → `department_directory.department_id`
- 뜻 : AI가 추천한 부서 번호가 부서 목록의 실제 부서를 가리킴
- 자동 이관 없음 (`automatic_transfer` 항상 `false`), 추천은 참고용
- 그 외 연결 없음
  - 민원 글은 검색 자료에 들어가지 않음
  - 검색 자료는 민원 데이터를 바꾸지 않음

## 6. 민원 한 건의 흐름

1. 시민이 민원 작성 → `complaints` 저장 (처리 기한 `due_at`도 함께 정함)
2. AI 작업 생성 → `ai_jobs` 저장
3. AI가 `complaint_rag`에서 FAQ와 사례 검색 (읽기만)
4. 결과 저장 → `ai_results` (근거, 추천 부서, 답변 초안), 진행 기록은 `job_events`
5. 답변 초안 → `messages`와 `message_versions`에 초안으로 저장
6. 담당자가 배정, 열람, 계획, 조치를 하면 `complaint_events`에 한 줄씩 쌓임
7. 담당자가 수정하고 게시 → `message_versions`에 새 버전 추가, 게시된 버전 1개 지정

## 7. 실행 방법

- 파일 2개
  - `01_complaint_rag.sql` : `complaint_rag` 생성 (pgvector 확장 필요)
  - `02_complaint_app.sql` : `complaint_app` 생성
- 순서 : `01` 먼저, 그 다음 `02`
- 명령 : `psql -d DB이름 -f 01_complaint_rag.sql`, `psql -d DB이름 -f 02_complaint_app.sql`
- `02`는 여러 번 실행 가능 : 맨 위에서 `complaint_app`만 지우고 다시 생성
- `02`는 `complaint_rag`를 건드리지 않음
- `complaint_rag`가 없는 DB : 부서 연결만 건너뛰고 나머지는 정상 실행

## 8. 값 정의 (프로토타입 HTML 기준)

- 처리 상태(`complaints.status`) 10가지 : AI검토, 배정완료, 처리중, 보완요청, 답변완료, 총괄검토, 조정대기, 재배정, 반려, 소관외 종결
- 단계(`complaints.stage`) 1부터 5까지
  - 1 접수, 2 AI검토, 3 배정, 4 처리중, 5 답변완료
- 공개 구분(`job_events.vis`) 3가지
  - `pub` : 자동 공개
  - `int` : 내부 전용
  - `ai` : AI 산출
- 공개 구분(`complaint_events.vis`) 2가지 : `pub`, `int`
- 민원번호(`complaints.public_code`) : `YYYY-MMDD-NNNN` 형식 (예: 2026-1030-0001)
- 분류(`complaints.category`) : "대분류 › 중분류" 형식
- 처리 기한(`complaints.due_at`) : 접수 시 정함. 시연은 접수 후 5일. 기한 연장이 승인되면 값을 바꾸고 이력을 `complaint_events`에 남김

## 9-1. 화면을 서버(API)에 연결하는 방법

- 화면(`프로토타입_DB샘플연동.html`)이 데이터를 받는 곳은 한 군데(`DATA`)뿐
- 기본 : HTML 안에 들어 있는 샘플 JSON을 씀
- 서버 연결 : 주소 뒤에 `?api=서버주소`를 붙이면 서버에서 받아 화면을 다시 그림
  - 예) `프로토타입_DB샘플연동.html?api=http://서버주소:8000/api`
- 서버가 줘야 하는 것 : `GET {api}/{테이블이름}` → 샘플 JSON과 같은 모양의 배열
  - 테이블이름 : `users`, `complaints`, `ai_jobs`, `ai_results`, `messages`, `message_versions`, `job_events`, `complaint_events`
- 서버 연결에 실패하면 샘플 데이터로 그대로 보여 주고, 브라우저 콘솔에 이유를 남김
- 지금은 읽기만 가능 (민원 작성, 배정 등 화면에서 바꾼 값은 서버에 저장되지 않음). 저장은 API가 정해진 뒤 추가

## 10. 아직 정해지지 않은 것

- AI가 신뢰도를 줄 수 있는지 : 승현님 확인 필요 (안 주면 칸은 비워 두고 화면에는 '-'로 표시)
- AI 작업 단계(`ai_jobs.stage`) 값 : AI 쪽 흐름에 맞춰 결정
- DB 실행 위치 : `complaint_rag`가 들어 있는 DB를 쓸지 확인 필요
- 프로토타입 코드에는 "질문대기", "추가문의"도 상태처럼 쓰이나 데이터 모델의 상태 10가지에는 없음 (현재 SQL은 10가지만 허용)
- 첨부파일 테이블 : 아직 없음
- 긴급 표시, 특이민원 표시, AI 요약의 요청과 감정 줄 : AI 결과 형태가 정해진 뒤 결정
- 협조 요청의 받는 부서, 기한 연장의 승인 상태 : 지금은 이력 한 줄(`body`)로만 남음
