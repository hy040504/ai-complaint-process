## 0. 문서 사용 안내

이 문서는 **「보트랩 VoteLab _ AI 민원 상세 기획안 - 산학공동.pdf」(54쪽, 버전 1.0, 2026-10-15)**의 화면·기능 정의와 개발 상세 설계를 읽기 쉬운 구조로 재작성한 분석 자료다. 시스템을 구현하거나 다른 AI가 문서를 검색·요약할 때 핵심 개념, 역할, 데이터, 상태 규칙, 예외, 성능 기준을 빠르게 파악할 수 있도록 구성했다.

- **대상 시스템:** AI 기반 스마트 민원 처리 및 진행상황 시각화 시스템
- **대상 기관/업무 맥락:** 청주시 민원 접수·배정·처리 지원을 예시로 한 공공 행정 시스템

## 1. 문서가 정의하는 범위

이 자료는 아이디어 소개 수준이 아니라 **동작하는 프로토타입을 운영 시스템으로 전환하기 위한 구현 명세**에 가깝다. 화면 배치와 문구, 버튼 동작은 참조 프로토타입을 기준으로 삼고, 문서에는 이를 실제 개발에 필요한 데이터 모델, API, 서버 규칙, 알림, 검수 기준으로 풀어 썼다.

| 구분 | 문서에서 정의한 범위 |
|---|---|
| 사용자 화면 | 시민 웹, 민원과 콘솔, 담당자 워크스테이션, 관리자 대시보드 |
| 기본 규모 | 주요 역할 4종, 화면 46개, 기능 60개, REST API 69개 및 SSE |

| AI 범위 | 개인정보 마스킹, 긴급·FAQ·처분성 판정, 규칙 기반 분류와 라우팅, 중복 탐지, RAG 답변 초안·요약 |
| 시스템 범위 | 인증, SMS, 감사, 통계, 정책 후보 발굴, 기관 설정, 시범운영 및 인수시험 |

## 2. 해결하려는 문제와 설계 목표

### 2.1 기존 민원 흐름의 불편

1. 시민이 먼저 본인인증을 하고 담당 부서를 직접 골라야 하는 경우가 있다.
2. 단순한 서류·절차 질문에도 정식 접수 절차가 요구되거나, 필요한 정보를 찾기 어렵다.
3. 담당 부서가 정확하지 않으면 접수 후 재배정·반려가 반복될 수 있다.
4. 접수 뒤 시민이 처리 상황을 알기 어려워 확인 전화를 하게 된다.
5. 담당자는 분류·배정, 진행상황 설명, 추가 질문 대응, 답변 작성 등을 수작업으로 수행한다.
6. 특이민원 대응과 원문 열람은 직원 보호와 법적 증적 관리가 필요하다.
7. 민원 데이터가 통계에서 끝나지 않고 정책 과제의 근거로 연결되기 어렵다.

### 2.2 목표 경험

- 시민: **묻고 → 필요한 경우에만 접수하고 → 진행을 확인한다.**
- 민원과: **미배정·반려·기한 임박 건을 한 큐에서 배정하고 관리한다.**
- 담당자: **전달된 업무를 단계별로 처리하며, 별도 상태 입력 없이 처리 행동이 진행 표시로 이어진다.**
- 관리자: **처리 성과와 위험 신호를 보고, 반복·급증 민원을 정책 과제로 전환한다.**

### 2.3 설계 원칙

1. **질문이 먼저, 인증은 등록 시점에:** 익명 상담으로 해결되는 문의는 접수·인증 없이 마칠 수 있다.
2. **근거 없는 AI 답변은 표시하지 않음:** 조례·편람·처리 이력 근거를 붙이고, 근거가 없으면 사람 확인으로 전환한다.
3. **분류·배정은 재현 가능한 규칙으로:** TAXO 분류 사전과 점수 규칙으로 담당 부서 후보를 산출한다. LLM은 동의어 확장·요약·초안 등 보조 역할이다.
4. **업무 행위가 진행 상황:** 담당자의 열람·계획·현장 확인·결재 등이 이벤트가 되어 시민 상태를 갱신한다.
5. **공개 범위는 서버가 결정:** 내부 메모·마스킹·특이민원 신호 등은 서버 직렬화 단계에서 제거한다.
6. **행정 답변은 사람 승인 후 전달:** AI는 답변 초안을 만들 수 있지만, 정식 답변은 전결 또는 민원과 확인이 필요하다.
7. **직원 보호:** 특이민원은 순화 요약을 우선 보여주고, 원문을 열람할 때는 목적 선택과 감사 기록을 요구한다.
8. **민원 데이터를 정책으로 연결:** 유형·시기·지역·시간대 등의 집계를 정책 후보와 시행 효과 측정에 활용한다.

## 3. 용어와 서로 다른 상태 단계

| 용어 | 뜻 |
|---|---|
| **Case / 민원** | 접수번호를 가진 하나의 민원 레코드. 이후 질문·답변·재검토·중복 병합 기록을 같은 민원에 이어 붙인다. |
| **Event / 이벤트** | 민원 처리 과정에서 발생한 행위와 상태 변경 기록. 순번 `seq`를 갖고 시민 공개 문구, 공개 여부, 문자 발송 여부를 담을 수 있다. |
| **stage** | 시민 트래커에 표시하는 큰 진행 단계 5개. 접수, AI 검토, 부서 배정, 처리 중, 답변 완료. |
| **status** | stage 안의 구체 상태. 예: 조정대기, 질문대기, 보완요청, 반려, 추가문의, 재검토, 소관외 종결. |
| **민원과 7단계** | 접수 확인 → 분류 검토 → 배정 → 양식 전달 → 열람 확인 → 처리 모니터링 → 종결. 민원과 내부 업무 절차다. |
| **담당자 7단계** | 배정 수신 → 업무 열람 → 조치 계획 → 현장 조치 → AI 답변 초안 → 결재 → 민원인 답변. 실제 부서 처리 절차다. |
| **TAXO** | 유형별 대·중분류, 키워드, 주관 부서, 대체 후보, 신뢰도, 긴급·모호 플래그, 안내문, 처리일, 폼 정의 등을 가진 분류 사전. |
| **conf** | 분류 신뢰도 값(0~1). 임계값과 후보 수 등을 이용해 자동 배정 또는 사람 검토 경로를 선택한다. |
| **ambiguous** | 소관 부서가 불분명하거나 여러 부서가 관련되는 경우를 나타내는 플래그. |
| **inquiry** | 단순 질의·절차 안내 등 부서에 업무를 배정하지 않고 민원과가 답변할 수 있는 문의형인지 나타내는 플래그. |
| **form** | 민원과에서 담당 부서로 보내는 업무 전달 양식. 작성(draft), 전달(sent), 열람(opened), 반려(returned) 상태를 가진다. |
| **purpose** | 업무 양식의 목적. 일반 부서 전달, 보좌관의 소관 판단 요청, 민원과 자체 처리 등을 구분한다. |
| **RAG** | 조례·편람·FAQ 등에서 관련 근거를 검색한 다음 그 근거를 바탕으로 답변 초안을 생성하는 방식. |
| **TAXO 점수 분류** | 미리 정한 키워드·유형 규칙으로 분류 점수를 계산하는 결정론적 분류. 이 문서에서 실제 배정의 기준이 되는 핵심 로직이다. |
| **SSE** | 서버에서 브라우저로 실시간 이벤트를 전달하는 방식. 재접속 시 마지막 이벤트 순번부터 이어받는다. |
| **Outbox** | 상태 변경과 알림 메시지를 같은 데이터베이스 트랜잭션에 기록해, 커밋 뒤 워커가 SMS·SSE를 전송하도록 하는 패턴. |

**중요:** 시민 트래커의 5단계, 민원과의 7단계, 담당자 처리의 7단계는 서로 다른 관점의 절차다. 화면에는 각각 다른 진행 표시로 나타나며 서로 섞어 해석하면 안 된다.

## 4. 사용자와 권한

문서는 주요 화면 역할을 시민·민원과·담당자·관리자 네 그룹으로 묶는다. 실제 운영상 보좌관, 결재권자, 감사·법무 담당은 별도 권한이 필요한 보조 역할이다.

| 사용자 | 주 화면 | 책임 |
|---|---|---|
| 시민·방문자 | 모바일 우선 공개 웹, 문자 링크 | 익명 상담, 정식 민원 등록, 진행 확인, 질문 답변, 보완자료 제출, 만족도·재검토 |
| 민원과(총괄과) | 청내망 콘솔 | 접수 큐 분류·배정, 자동 배정 검수, 보좌관 요청, 문의 답변, 소관 외 안내, 추가 질문·재검토, 특이민원·서류발급 관리 |
| 보좌관 | 청내망 내 제한 화면 | 소관이 갈리는 민원의 주관 부서와 협조 부서 판단 |
| 담당 부서 실무자 | 청내망 워크스테이션 | 전달 업무 열람, 담당자 지정, 조치 계획·현장 처리·협조·보완·답변 초안 작성, 결재 상신 |
| 결재권자 | 담당자 콘솔의 결재함 | 팀장 검토, 과장 전결, 반송 |
| 관리자·정책 담당 | 관리자 대시보드 | 기관 현황·통계·임계값·분류 사전·지식베이스·공지·정책 단계 관리 |
| 감사·법무 | 읽기 중심의 별도 권한 | 원문 열람·감사 증적 확인, 특이민원 대응 지원 |

권한은 화면에서 버튼을 숨기는 것으로 끝나지 않는다. **서버의 모든 쓰기 API가 역할·부서·민원 상태를 재검증**해야 한다. 직원은 청내망 SSO, 시민은 등록 시점의 휴대폰 본인확인을 사용한다.

## 5. 전체 시스템 구조

### 5.1 논리 구성

1. **채널:** 설치 없는 시민 웹, 문자 링크, 청내망 콘솔.
2. **API Gateway:** REST 요청·SSE 연결, 익명 세션·시민 토큰·직원 SSO 인증, 요청 제한.
3. **Case Service:** 민원 생성·조회·상태 전이·이벤트 순번 관리. 모든 쓰기 동작의 단일 관문.
4. **AI Pipeline:** PII 마스킹, 긴급·FAQ·처분성 판정, TAXO 분류·라우팅, 유사 민원 탐지, RAG 검색·초안 생성.
5. **Assignment / Workflow:** 업무 양식, 자동·수동 배정, 보좌관 판단, 담당자 7단계 처리, 협조·보완·연장·결재.
6. **Notification:** 이벤트를 시민용 문구로 바꾸고 SMS·SSE를 Outbox 워커로 전달.
7. **Analytics / Protection:** 통계와 정책 후보 산출, 특이민원 위험 신호·순화 요약·감사.
8. **저장소·외부 연계:** PostgreSQL, pgvector, 객체 저장소, 본인확인기관, 기관 SMS, 직원 SSO, LLM 또는 온프레미스 모델.

모든 화면은 같은 민원 레코드와 이벤트 스트림을 보지만 역할별로 받을 수 있는 필드가 다르다. 상태 변경은 Case Service 한 곳에서만 일어나게 한다.

### 5.2 권고 기술 스택

| 계층 | 계획서의 권고 |
|---|---|
| 프론트엔드 | React 18 + TypeScript. 시민 웹과 청내망 콘솔을 별도 SPA로 구성하고 SSE 구독·쿼리 캐시 사용 |
| 백엔드 | Node.js/NestJS 또는 Spring Boot. REST + SSE |
| 데이터베이스 | PostgreSQL 15 이상, JSONB, pgvector |
| 백그라운드 작업 | DB 기반 잡 큐(pg-boss 또는 Quartz), Outbox 워커 |
| AI | 결정론적 TAXO 규칙 엔진 + 교체 가능한 LLM API 또는 온프레미스 sLLM + 임베딩 |
| 인증·알림 | 시민 휴대폰 본인확인기관 API, 직원 청내망 SSO, 기관 SMS Gateway |
| 관측성 | JSON 구조화 로그, Prometheus 호환 메트릭, 요청→이벤트→문자 추적 ID |

### 5.3 배포·망 분리

- 시민 정적 웹과 공개 API는 DMZ에 둔다.
- 업무 서버·DB·직원 콘솔과 감사 로그는 청내망에 둔다.
- 외부 LLM으로 보내는 텍스트는 마스킹·비식별 처리 후 허용 목록을 통해서만 전송한다.
- DMZ에는 원문과 개인정보를 저장하지 않는다는 설계 원칙이 있다.
- LLM은 어댑터로 감싸 외부 API에서 온프레미스 sLLM으로 교체할 수 있게 한다.
- SMS, 본인확인, LLM 등 외부 연계가 불가한 경우의 대체 경로와 개발용 모의 서버가 필요하다.

## 6. 시민 접수 경험: 질문을 먼저, 인증은 나중에

### 6.1 익명 상담 단계

1. 시민이 홈에서 자유 문장으로 질문하거나 자주 찾는 서비스 문구를 선택한다.
2. 익명 세션 토큰으로 상담을 시작한다. 이 단계에서는 본인인증을 요구하지 않는다.
3. 전송 전·서버 저장 전 개인정보를 탐지해 마스킹하고, 어떤 항목을 가렸는지 안내한다.
4. 화재·가스·붕괴·폭발·감전·침수·인명사고 등의 긴급 키워드는 119·112 배너를 최우선 표시한다. 민원 접수는 병행 가능하되 긴급전화 안내를 대체하지 않는다.
5. 유형, 예상 부서, 긴급도, 신뢰도, 필요한 보충정보를 분석 카드와 상황별 안내(tip)로 보여준다.
6. FAQ 근거가 충분하면 출처 칩이 붙은 안내를 제공한다. 시민이 해결됐다고 표시하면 인증·정식 접수 없이 상담을 종결한다.
7. 처분성·재량성 사안은 AI가 답변하지 않고 접수번호 발급 및 담당자 검토 경로로 안내한다.
8. 일반 접수는 동적 폼으로 이어진다. 내용 수정은 재분석하며 같은 내용 수정으로 새 민원을 만들지 않는다.
9. 유사 민원이 발견되면 기존 건에 함께 처리할지 별도 접수할지 시민에게 묻는다.

### 6.2 정식 등록 단계

- 접수 내용을 필요한 범위로 보완하고 임시 저장할 수 있다.
- 등록 제출 시에만 본인인증을 요구한다.
- 인증에 실패해도 폼은 `pendingForm`으로 보관하고, 성공하면 같은 Idempotency-Key로 등록을 다시 시도한다.
- 재전송 때문에 같은 민원이 중복 생성되지 않도록 서버 멱등성 규칙을 적용한다.
- 접수 성공 후 접수번호, 진행 트래커, 문자 안내를 제공한다.

### 6.3 동적 접수 폼

TAXO 유형 또는 정규식 기반 폼 명세로 필요한 정보만 묻는다.

| 폼 종류 | 요구 예시 | UX 원칙 |
|---|---|---|
| 버스 노선 | 내용, 노선 번호·구간, 시간대 | 불필요한 주소·사진을 요구하지 않는다. |
| 행사·기간 | 행사명, 기간, 선택적 위치 | 시간 범위를 명확히 받는다. |
| 소음 | 시간대, 위치, 선택적 녹음 파일 | 시간대는 심야·아침·주간·저녁 등 선택형으로 제공한다. |
| 주정차 | 차량번호, 위치, 사진 | 차량번호는 단속 관련 업무정보로 취급해 PII 마스킹 대상에서 제외한다고 문서는 명시한다. 기관 정책에 맞는 별도 개인정보 검토가 필요하다. |
| 시설 파손 | 위치, 사진 | 가까운 건물명 등 입력 대안을 허용한다. |
| 서류 발급 | 서류 관련 내용 | 민원과의 서류 발급 4단계로 연결한다. |
| 기본형 | 내용, 선택적 위치·첨부 | 필요한 정보를 최소화한다. |

필수 필드는 화면과 서버가 동일하게 검증한다. 누락 시 화면에서 표시하고 API는 422를 반환한다. 임시 폼은 24시간 보관 후 만료되며, 인증 완료 시 세션 소유에서 시민 계정으로 승계할 수 있다.

### 6.4 시민의 후속 화면

- **C-04 나의 민원:** 전체·진행 중·완료 필터와 민원 카드.
- **C-05 진행 트래커:** stage 5단계, 공개 이벤트, 배정 신뢰도·근거, 질문 답변, 부서 대표 연락처. 담당자 개인 연락처는 공개하지 않는다.
- **C-06 답변서·만족도:** 게시 답변, 근거 원문 칩, 처리기간, 1~5점 만족도.
- **재검토:** 만족도 2점 이하이고 답변 후 30일 이내일 때 요청 가능.
- **C-06f 추가 문의:** 기존 건에 이어 붙이며, 대기 중인 질의가 있으면 새 질문은 막는다.
- **C-07 보완 제출:** 문자 서명 토큰 또는 인증을 이용해 자료를 제출하고 처리를 재개한다.
- **C-08 문자:** 발송 문구와 발송 시각 확인. 링크 토큰은 7일·해당 민원 1건에 한정한다.
- **C-09 내 정보:** 문자 수신, 큰 글씨, 개인정보 안내, 전화·방문 안내.
- **C-11/12:** 지역 공지 및 자주 찾는 서비스 12종.

## 7. AI 판단·분류·라우팅

### 7.1 처리 순서

계획서의 실제 분류·접수 흐름은 다음과 같이 해석할 수 있다.

1. **입력 마스킹:** 휴대폰, 주민등록번호, 카드번호, 계좌번호, 이메일 등을 탐지하고 마스킹한다.
2. **긴급 탐지:** 긴급 키워드가 있으면 긴급 표시와 119·112 안내를 먼저 제공한다.
3. **FAQ 탐색:** FAQ 키워드와 유효한 지식베이스 근거가 함께 있을 때 즉시 안내한다.
4. **처분성 차단:** 보상·배상·허가·과태료·처분·소송·법령 해석 등은 AI 답변을 막고 담당자 검토로 넘긴다.
5. **TAXO 점수 계산:** 분류 사전의 키워드 일치 길이 등을 점수화하고 문의형·의문 표현 관련 보정치를 더한다.
6. **후보 구성:** 주관 부서와 대체 후보 부서를 만든다. 소관 모호성(ambiguous), 긴급도, 문의 여부를 함께 둔다.
7. **상황별 안내:** 유형별 처리 안내, 예상 일수, 필요한 입력 필드를 제시한다.
8. **동적 폼 구성:** 유형별 필수·선택 필드를 생성한다.
9. **중복 탐지:** 최근 30일·같은 읍면동의 문장과 한글 bigram을 비교해 유사 건을 제안한다.
10. **자동 배정 여부:** 신뢰도·후보 수·유형·특이민원 여부 등 명시된 조건을 모두 확인한다.
11. **LLM 보조:** 요약·동의어 확장·RAG 초안 작성 등에만 사용한다. 분류와 라우팅의 기준은 결정론적 규칙이다.

### 7.2 자동 배정의 기본 조건

계획서의 예시 기본 임계값은 `thresholds.assign = 0.70`이다. 다음 조건을 모두 충족해야 자동 배정한다.

- `conf >= 임계값`
- 후보 부서가 한 곳(`len(cands) == 1`)
- 문의형이 아님
- 소관 검토 대상이 아님
- 특이민원이 아님
- 민원총괄과 자체 소관이 아님

조건이 충족되면 업무 전달 양식을 자동 생성·전달하고, 담당 부서의 미열람 큐에 넣는다. 민원과에는 사후 검수 대상이 표시된다. 조건을 충족하지 않으면 민원과가 배정하거나 보좌관 판단을 요청한다. **임계값 이상이라는 이유만으로 모든 민원이 자동으로 배정되는 것은 아니다.**

### 7.3 처리 경로 세 가지

| 경로 | 예시 | 자동화 | 사람의 결정 |
|---|---|---|---|
| FAQ·단순 문의 즉시 안내 | 서류·절차·자주 묻는 질문 | 근거가 확보되면 AI가 안내하고 익명 상담에서 해결 종결 가능 | 근거 부족, 복합 질문은 민원과 확인으로 전환 |
| 일반 민원·AI 보조 배정 | 도로시설, 생활 불편, 일반 신고 | 분류·요약·부서 추천·업무 양식 작성 | 민원과가 모호한 소관을 판단하고, 담당자가 처리·답변 |
| 처분성·긴급·특이 사안 | 허가·보상·법령 해석·긴급 안전·특이민원 | AI는 긴급 안내·분류·순화 요약 등 보조 | AI 단독 답변·처분 금지. 담당 부서·전담부서·긴급기관으로 이관 |

### 7.4 TAXO 분류 사전

TAXO 레코드는 대략 다음 항목을 가진다.

- 대분류·중분류 및 키
- 검색 키워드
- 주관 부서·대체 부서 목록
- 기본 점수 또는 신뢰도
- 소관 모호성·긴급 플래그
- 부서가 갈리는 이유(`why`)
- 시민 안내문(`tip`)
- 기본 예상 처리일(`days`)
- 유형별 접수 폼과 필수 필드
- 문의형 여부와 FAQ 답변 참조
- 버전 정보

관리자는 반려·오배정 사유를 검토해 키워드와 후보 부서의 변경안을 만들고 승인한다. 승인 시 TAXO 버전을 올리고 변경 감사를 기록한다. **AI가 반려 데이터를 자동으로 바로 학습해 분류 기준을 바꾸는 구조가 아니라, 관리자 승인 후 규칙 사전을 갱신하는 구조**다.

## 8. 상태 머신과 업무 전이

### 8.1 시민에게 보이는 5단계

| stage | 시민 표시 | 대표 status | 보통 다음 전이 |
|---|---|---|---|
| 1 | 접수 완료 | 접수 | 접수 생성 트랜잭션 안에서 AI 검토로 이동 |
| 2 | AI 1차 검토 | AI검토, 총괄검토, 조정대기, 질문대기, 재배정, 반려 | 민원과·보좌관 판단, 문의 답변 또는 소관 외 안내 |
| 3 | 담당 부서 배정 | 배정완료 | 담당자가 업무를 열람하고 조치 계획 등록 |
| 4 | 처리 중 | 처리중, 보완요청, 추가문의, 재검토 | 조치 완료 후 결재 또는 추가 질문 응답 |
| 5 | 답변 완료 | 답변완료, 소관외 종결 | 추가 문의·재검토 요청이 가능하면 stage 4로 되돌림/보완 |

시민은 stage와 공개 이벤트만 본다. 예를 들어 내부 `조정대기`는 “담당 부서를 확인하고 있습니다”와 같이 번역하고, 내부 `반려`는 “담당 부서를 다시 확인하고 있습니다”로 표시한다. 내부 상태명이나 업무 메모가 그대로 공개되지 않는다.

### 8.2 담당 부서의 7단계 처리

1. 배정 수신 확인
2. 업무 열람 및 담당자 지정
3. 조치 계획 등록(방법·예정일·예상 소요 등)
4. 현장 조치(현장 일정, 협조 요청, 보완 요청, 조치 결과)
5. 근거를 붙인 AI 답변 초안 작성·수정
6. 담당자 기안 → 팀장 검토 → 과장 전결
7. 답변서 게시·문자 통보·결과 확인

담당자가 조치 계획을 등록하면 시민에게 예정일 안내, 현장 일정을 등록하면 “현장 확인 중”, 협조를 보내면 “관련 부서와 협의 중”처럼 공개 문구가 자동으로 만들어진다.

### 8.3 민원과의 7단계

접수 확인 → 분류 검토 → 배정 → 양식 전달 → 열람 확인 → 처리 모니터링 → 종결.

상태별로 현재 필요한 액션 블록만 보여준다. 민원과에는 담당자 반려 버튼이 없다. 관할 밖 민원은 소관 외 템플릿을 편집해 안내·종결한다. 보좌관은 주관·협조 부서가 겹치는 민원에 한해 판단 요청을 받는다.

### 8.4 반려·협조·연장·재검토

- **담당 부서 반려:** 허용된 단계에서 정해진 사유를 선택한다. 민원은 stage 2로 돌아가고 민원과 큐에 표시되며, 자동배정이었다면 오배정 기록으로 환류한다.
- **협조 요청:** 담당 부서가 다른 부서에 협조를 보낸다. 기본 회신 기한은 3일이며, 회신 이벤트는 시민에게 “협의 완료”로 반영할 수 있다.
- **기한 연장:** 담당자가 사유와 1~14일 연장 일수를 요청한다. 민원과가 승인해야만 실제 기한이 변경된다. 승인 시 사유를 시민에게 알린다.
- **추가 질문:** 민원과가 시민에게 위치·사진·시점 등의 보충 질문을 보낸다. 시민 답변을 같은 민원에 기록하고 배정 절차를 이어간다.
- **추가 문의:** 답변 후 시민이 추가 질의를 남긴다. 같은 민원에 이어 붙이고 대기 질의는 한 건으로 제한한다.
- **재검토:** 답변 후 30일 이내, 만족도 2점 이하인 경우 요청할 수 있다. 민원과가 보완 재전달, 기존 답변 유지, 다른 부서 재배정 중 결정한다.
- **유사 민원 일괄 처리:** 각 민원번호를 병합하지 않는다. 동일한 처리 이벤트를 건별로 만들고 시민별 문자를 보낸다.

### 8.5 법정 기간과 내부 SLA

문서는 민원 유형별 법정 처리기간과 TAXO의 시스템 기본 D-day를 구분한다. 긴급 민원은 업무 전달 기한 기본 접수일+2일, 일반은 +5일의 예시를 둔다. 시민의 법정·유형별 표시 기한은 TAXO.days 또는 유형 기준으로 결정한다. 매일 00:10에 기한을 다시 계산하고 D-3·D-1 알림, D-0 경보를 생성한다.

공휴일·토요일 산입, 시간 계산, 연장 한도는 법무 검토 후 확정하라고 명시한다. 담당자 업무 전달 목표, 협조 회신 SLA 3일, 보좌관 판단 48시간 재촉·72시간 총괄 강제배정 옵션은 법정 처리기간과 별개의 **내부 운영 규칙**이다.

## 10. RAG 답변·문자·시민 공개 규칙

### 10.1 답변 생성

- 담당자용 답변 초안은 조례·민원편람·처리 이력 등을 검색한 뒤 근거 칩을 붙여 만든다.
- 문의형 초안도 편집 가능하며 민원과가 확인한 뒤 전달한다.
- 근거가 없으면 답변을 렌더링하지 않는다.
- AI가 초안을 만들더라도 정식 답변은 결재 전결 또는 민원과 확인 없이 시민에게 도달할 수 없다.
- 법령 해석, 인허가, 보상, 과태료, 재량·처분 판단을 AI가 단독으로 답하지 않는다.

### 10.2 중요한 경계: 익명 FAQ와 공식 민원 답변

문서에는 FAQ 근거 답변을 익명 상담에서 제공하고, 시민이 해결됐다고 하면 정식 접수 없이 종결할 수 있다고 되어 있다. 한편 “어떤 답변도 결재 전결 또는 민원과 확인 없이 시민에게 도달할 수 없다”는 불변 규칙도 있다.

이 둘은 다음처럼 구분해야 일관된다.

- **익명 상담 단계의 일반 정보 안내:** 정식 민원 답변이나 행정처분이 아닌, 승인된 FAQ·공식 근거를 보여주는 자기 안내로 제한한다.
- **접수번호가 발급된 민원의 공식 답변:** 반드시 민원과 확인 또는 담당자 결재를 통과한다.
- 이 구분을 API·화면 문구·감사 로그·법적 고지에 명확히 반영해야 한다. 프로토타입/운영 구현에서 구분이 불명확하다면 배포 전에 명세를 확정해야 한다.

### 10.3 시민 문구와 SMS

이벤트의 `cz`(citizen-facing text)가 화면·문자 문구의 단일 원천이다. 내부 행위 설명 `act`와 시민 문구 `cz`는 다르다. 문자 수신을 끈 시민에게도 웹 트래커에는 같은 공개 문구를 남긴다. 야간 21:00~08:00 발송은 긴급·보완 요청을 제외하고 08:00에 모아 보낸다는 제안이 있다.

- 링크 토큰: 7일, 해당 건만 조회
- 문자 발송: Outbox 재시도 최대 5회, SMS 거부 시 웹만 제공
- 이벤트의 가시성: 공개(`pub`), 내부(`int`), AI 산출(`ai`) 등의 분류를 사용
- `vis:int` 또는 시민 문구가 빈 이벤트는 시민 API·SSE·문자에서 제거
- 문자에는 담당자 개인 연락처를 넣지 않으며, 공개 가능한 담당 부서·접수번호 중심으로 안내

## 11. 개인정보·직원 보호·감사

### 11.1 개인정보 보호 설계

1. 익명 상담은 개인정보를 요청하지 않는다.
2. 입력 텍스트는 클라이언트 1차, 서버 2차 마스킹을 수행한다.
3. 계획서 예시는 주민등록번호, 휴대전화번호, 카드번호, 계좌번호, 이메일 탐지를 든다.
4. 마스킹 전 원문은 서버 저장소·로그에 남기지 않는다는 원칙이다.
5. 첨부 이미지는 EXIF 위치 메타데이터를 제거하고 바이러스 검사 후 객체 저장소에 둔다.
6. 인증 단계에서 이름·생년월일·통신사 등 본인확인 정보를 검증 직후 파기하고, SMS용 휴대폰 번호는 암호화 저장한다.
7. 외부 LLM에는 마스킹·비식별된 내용만 보내며, 학습 이용 금지 계약 또는 온프레미스 모델을 사용한다.
8. 역할에 따라 원문·이벤트·담당자 이름·업무 자료를 다른 형태로 직렬화한다.
9. 감사 로그는 append-only로 두며 원문 열람에는 목적 선택과 열람 감사가 필요하다.

**구현 시 확인:** 문서에는 익명 세션/상담 메모리 30분, 임시 폼 24시간, 서명 링크 7일, Outbox 발송 후 90일, 감사 로그 최소 5년(기관 기준) 등의 서로 다른 보존 정책이 있다. 각각 어떤 자료에 적용되는지 보존표와 실제 기관 기록물 기준을 대조해야 한다.

### 11.2 특이민원 보호

계획서는 8개 위험 신호를 탐지·분류하는 보호 흐름을 제시한다.

- 반복·집착성(동일 발신자·동일 사안 반복)
- 욕설·협박·모욕
- 성희롱·언어 성폭력
- 장시간 통화·면담
- 법적 위협·고소·소송 발언
- 재난·긴급 사안
- 담당자 개인 연락처·주소 등 직무 외 개인정보 요구
- 처분성·재량성 민원

특이민원 화면은 **순화 요약을 우선 표시**하고, 원문 열람 시 사실 확인·법적 대응·상급 보고 등 목적을 고르게 한 뒤 감사 로그를 남긴다. 정당한 요구 내용은 감정 표현과 분리해 일반 민원 처리 절차에서 놓치지 않도록 한다. 발생보고서를 작성하고 보호조치 승인·법무 검토·종결을 기록한다.

### 11.3 운영상 주의

- 위험 신호는 자동 처벌이나 시민 차단 판단의 근거로 단독 사용하지 않는다.
- 계획서도 오탐 방지를 위해 회부는 사람이 결정하고 신호는 배지로 표시하는 방향을 제시한다.
- 재난 키워드 탐지 결과는 실제 긴급기관 연락을 대체하지 않는다.
- 30분 안내·60분 종결 등 통화 규칙과 증적 보존은 현행 법령·기관 규정 및 실제 운영 지침 확인이 필요하다.
- 원문 접근, 군집 열람, 설정 변경, 서류 발급, 보호조치 등 민감 동작은 목적·행위자·시각·대상 기준으로 감사한다.

| `draft` | 세션 또는 시민 소유의 24시간 임시 저장 폼 |

### 12.2 핵심 민원 필드

민원번호, 데이터 버전, 접수자, 제목, 마스킹된 원문, stage/status, 현재 부서, 분류 신뢰도, 대·중분류, 후보 부서, 모호·문의·긴급·특이 플래그, 자동 배정·검수 여부, 반려 기록, 보좌관 결정, 주소·첨부·부가 메타데이터, 개인정보 마스킹 내역, AI 요약 카드, 조치 계획·현장 결과, 기한 연장, 초안·결재·게시 답변, 보완 요청, 만족도, D-day, 담당자, 접수·종결 시각 등을 포함한다.

### 12.3 이벤트의 의미

이벤트에는 단조 증가하는 `seq`, 내부 행위 `act`, 시민 공개 문구 `cz`, 가시성 `vis`, 문자 발송 여부 `sms`, 행위자, 시각이 있다.

- `seq`는 SSE 이벤트 ID와 같아서 끊긴 연결의 재개에 사용한다.
- 이벤트는 상태 전이의 설명이자 타임라인·알림·감사·분석 데이터다.
- 시민에게는 공개 이벤트만 전달하고 `act`·직원 이름을 제거하며, 담당자에게는 자기 부서 업무, 민원과·관리자에게는 권한 범위 내 정보를 제공한다.
- 새 민원번호를 만들지 않고 기존 민원의 event history에 질문·재검토·중복 처리 기록을 이어 붙이는 것이 기본이다.

## 13. API·서버 동작 규약

### 13.1 API 그룹

문서는 총 69개 REST API와 SSE를 예정한다. 주요 API 그룹은 다음과 같다.

- 익명 상담: 세션 생성, AI 분석·마스킹·중복 탐지, 초안·임시 저장
- 시민: OTP·인증, 민원 생성·조회, 공개 타임라인, 보완 제출, 만족도, 질문 답변, 추가 문의, 재검토, 공지·빠른 서비스
- 민원과: 큐, 배정, 보좌관 요청, 업무 양식 작성·전달, 자동 배정 검수, 문의 회신, 소관 외 답변, 추가 질문, 연장 승인, 유사 건 처리, 서류 발급, 원문 열람·발생보고서
- 담당자: 부서 업무·협조 조회, 양식 열람, 조치 계획, 현장 처리, 보완 요청, 협조·연장·반려·특이민원, 초안·결재
- 관리자: 통계·분류 축, 임계치, 특이민원 상태, TAXO 반영, 공지, 정책 단계·협의·예산·심의, 감사 로그
- 실시간: `/api/events/stream` SSE, `Last-Event-ID` 재접속

### 13.2 상태 변경을 안전하게 처리하는 규칙

1. **원자성:** 한 번의 상태 전이에서 민원 갱신, 이벤트 삽입, 양식/질문/정책 갱신, Outbox 기록을 같은 DB 트랜잭션으로 커밋한다.
2. **멱등성:** 모든 쓰기 요청에 `Idempotency-Key`를 요구한다. 같은 키의 재요청은 최초 결과를 반환하고 키를 24시간 보관한다.
3. **허용 전이만 실행:** 서버가 현재 상태를 확인한다. 허용되지 않는 동작은 409 `TRANSITION_DENIED`와 현재 상태를 돌려준다.
4. **낙관적 잠금:** `Case.version`을 `If-Match`로 전달한다. 동시 수정 충돌은 409 `VERSION_CONFLICT`로 알려준다.
5. **이벤트 순서 보장:** SSE는 `Last-Event-ID`로 누락 이벤트를 재전송하고, 클라이언트는 순번이 역행하는 이벤트를 무시한다.
6. **역할별 응답 필터:** 클라이언트가 숨기는 방식이 아니라 서버가 응답 직렬화 단계에서 민감 필드를 제거한다.
7. **서버 시간 기준:** Asia/Seoul을 업무 기준으로 사용하고 저장은 타임존 포함 시각으로 한다.
8. **Outbox 발송:** DB 커밋 성공 뒤 워커가 문자를 재시도한다. 상태 저장과 알림 발송의 불일치를 줄인다.

### 13.3 대표 오류 코드

| HTTP | 코드 | 의미·처리 |
|---|---|---|
| 400 | `BAD_REQUEST` | 입력 형식 오류 |
| 401 | `AUTH_REQUIRED` | 등록 시 인증 필요. 폼 보관 후 인증하고 동일 키로 재전송 |

## 16. 개발 로드맵과 인수

### 16.1 계획된 기간

문서는 **준비 1주(W0) + 개발 8주(W1~W8) + 시범 운영 4주(W9~W12)**를 제안한다. 기간은 투입 인력·기관 협의에 따라 조정하는 값이다.

| 구간 | 주요 범위 | 관문 |
|---|---|---|
| W0 | 조직·업무분장·FAQ·조례 수집, 본인확인·SMS·SSO 연계 협의 | G1 착수 보고·연계 일정 |
| W1~W2 | 데이터 모델·인증·익명 세션·시민 웹 C-00~C-05·마스킹/분류/폼 | 분류 회귀 테스트 |
| W3~W4 | 민원과 큐·상세·배정·보좌관·담당자 D-01/D-02 초기 단계 | G2 중간 시연 |
| W5 | 답변·결재·문의·소관 외·반려·협조·연장·문자·SSE | 알림 문구 일치 검사 |
| W6 | 특이민원·감사·관리자 핵심 화면·추가 문의·재검토 | 1차 보안 점검 |
| W7 | 통계·11축 분류·정책 7단계·공지·서류발급·보고서 | 관리자 시연 |
| W8 | 인수 시나리오·접근성·성능·운영 이관 | G3 인수 시험 |
| W9~W12 | 시범 운영, KPI 실측, 분류 사전 튜닝, 문구 조정 | G4 최종 효과 보고 |

### 16.2 인수 테스트

프로토타입의 **시나리오 14종과 국내 사례 8종**을 테스트 케이스로 사용하고, 프로토타입 자동 검증의 분류·마스킹·긴급·특이·폼 결과와 운영 API 결과가 일치해야 한다.

- 인증 전 익명 질문과 FAQ 해결은 민원 생성 없이 종료된다.
- 정식 접수는 인증 실패 시에도 내용이 보존되고 인증 후 중복 없이 재개된다.
- 입력 한 줄로 화면 전환 없이 안내 카드가 표시된다.
- 유형별 폼에서 불필요한 필드가 빠지고 필수 필드 누락은 접수를 막는다.
- 휴대폰·주민번호가 DB·로그·민원과 화면에 원문으로 남지 않는다.
- 긴급 민원은 안내가 최우선이며 분류·기한 플래그도 맞다.
- 자동 배정 조건을 만족하는 건은 담당자 미열람 큐에 도착한다.
- 소관 불명 사례는 보좌관 결정 후 주관·협조 부서를 재작성한다.
- 담당자 7단계 필수 입력·결재 단계·시민 공개 문구가 일치한다.
- 반려·협조·연장·재검토가 지정된 상태 전이와 역할로만 수행된다.
- 전결 전 답변이 시민 화면·문자·SSE 어디에도 노출되지 않는다.
- 내부 메모·마스킹·회부 이벤트가 시민 응답에 포함되지 않는다.
- 임계값 변경이 분류 분기와 자동배정 조건에 즉시 반영된다.
- 동시 배정 충돌은 하나만 성공하고 나머지는 409로 최신화된다.
- SSE 재접속은 누락 이벤트를 재전송하고 역행 이벤트를 무시한다.

### 16.3 인수 체크리스트

- 14개 시나리오 + 8개 국내 사례와 참조 구현의 결과 일치
- 알림 문구표와 화면·SMS의 모든 트리거 일치
- 22개 역할 간 연동 경로 2초 이내 반영
- 마스킹 누락 0건, 정규식 회귀 및 무작위 1,000개 입력 시험

### 17.1 구현 전 명확히 합의할 항목

1. **익명 FAQ 답변과 공식 민원 답변의 경계:** FAQ는 즉시 안내 가능한 근거·문구·범위를 별도 승인 목록으로 관리할지 결정한다.
2. **법정 처리기간 산식:** 휴일·연장·시간대 및 민원 종류별 법정 계산을 법무·업무 담당자가 승인한다.
3. **자동 분류의 정답 라벨:** 최종 배정 부서와 최초 AI 추천 부서가 다른 경우 오답인지, 협조 부서를 포함할지 정의한다.
4. **통계 분모:** 전체 상담, 등록 민원, 중복 병합, 익명 종료, 재접수 등을 KPI에서 어떻게 분류할지 정한다.
5. **원문·첨부 접근과 보존:** 마스킹 후에도 민감성이 남는 텍스트·사진에 대한 별도 권한과 보유 기간을 확정한다.
6. **대체 운영 절차:** LLM·SMS·본인인증·SSO·SSE 장애 시 접수 누락 없이 수동 처리할 절차를 정한다.
7. **임계값 변경 승인:** 즉시 반영되는 설정에 대한 승인자·이력·롤백 절차를 마련한다.
8. **특이민원 시그널 사용 범위:** 시그널만으로 자동 차단·종결하지 않도록 화면과 API에 같은 가드를 둔다.

## 18. 이 문서를 AI가 사용할 때의 해석 규칙

1. **제안·예시·목표를 실적과 혼동하지 않는다.** 모든 KPI와 임계값은 계획서의 시범 기준이다.
2. **결정론적 분류와 LLM 역할을 구분한다.** 배정의 기본 근거는 TAXO 규칙이고 LLM은 보조다.
3. **시민 stage, 민원과 7단계, 담당자 7단계를 섞지 않는다.**
4. **익명 FAQ 안내와 정식 민원 답변을 구별한다.** 후자는 사람 승인 후 공개한다. 둘의 경계는 운영 전에 확정할 항목이다.
5. **AI가 행정처분·재량 판단을 한다고 설명하지 않는다.** 문서의 기본 원칙은 사람 검토·결재다.
6. **내부 필드·이벤트가 시민에게 보인다고 가정하지 않는다.** 공개 여부는 서버가 필터링한다.
7. **반려·재검토·추가 문의는 가능한 한 동일한 민원번호와 이벤트 이력으로 이어진다.**
8. **보좌관, 결재권자, 감사·법무는 네 개 주요 UI 역할 외의 보조 권한이다.**
9. **개인정보 원문은 저장하지 않는 것이 설계 원칙이며, 인증 후 SMS 목적의 전화번호는 암호화 보관한다는 예외를 함께 기록한다.**
10. **외부 법령·통계가 사실인지 묻는 경우 이 PDF만으로 검증됐다고 주장하지 않는다.** 해당 문서는 설계서이지 법률 검토서가 아니다.

## 19. 결론

VoteLab 기획안은 챗봇 하나를 만드는 계획이 아니라 **익명 상담 → 선택적 인증 접수 → 설명 가능한 부서 배정 → 담당자 업무 처리 → 시민 진행 공개 → 감사·통계 → 정책 환류**를 하나의 상태·이벤트 체계로 묶는 행정 플랫폼 설계다.

가장 중요한 기술적 선택은 **분류·라우팅을 규칙 기반으로 재현 가능하게 유지하고, LLM은 설명·요약·근거 기반 초안에 제한하는 것**, 그리고 **상태 변경·권한·공개 범위를 서버에서 강제하는 것**이다. 가장 중요한 실행 조건은 TAXO·지식베이스의 최신성, 기존 행정 시스템과의 연계, 개인정보·특이민원 처리 기준, 그리고 익명 정보 안내와 공식 답변의 경계를 먼저 확정하는 것이다.
