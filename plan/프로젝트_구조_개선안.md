## 2. 목표 구조 (제안)

```text
ai-complaint-process/
├─ README.md · AGENTS.md · CHANGELOG.md · setup.cmd · setup.sh
├─ bin/                 # 사용자가 실행하는 진입점만 모음 (한글 .cmd + .sh 한 쌍)
│    web, lab, search, assist, embed
├─ src/                 # 민원 웹·검사기·LLM·응대 (업무 서버)
│    ├─ complaints/     # 아래 5단계에서 repository/service를 하위 패키지로 분리
│    ├─ assist/ llm/ lab_web/
│    └─ search_client/  # 기존 src/search_client 이름 변경 (검색 API 클라이언트)
├─ rag/                 # 검색 엔진·색인 (이름 유지, origin이 원본의 단일 위치)
├─ ui/                  # 실제 화면 (목업은 ui/mockups/ 로 이동)
├─ scripts/
│    ├─ ops/            # 환경·DB·덤프·서비스 (영문 .sh 하나로 통일)
│    ├─ eval/           # 평가·비교 스크립트
│    └─ reports/        # 일자별 보고서 생성기 (공통 모듈 포함)
├─ docs/
│    ├─ harness/ cases/ # 현행 기준과 개발 기록 (유지)
│    ├─ reports/        # report + test 산출물 + 루트 PDF를 일자순으로 통합
│    └─ api/            # Swagger PDF 등 API 산출물
├─ plan/                # 현행 구현계획만 남기고 초기 기획 자료는 plan/archive/
└─ PACKET/              # 수집기 (유지)
```

## 3. 단계별 실행 계획 (위험이 낮은 순서)

| 단계 | 작업 | 위험 | 검증 |
| --- | --- | --- | --- |
| 1 | `db/`의 중복 JSON 삭제 후 `rag/origin/`을 단일 원본으로 지정. `db/load_samples.py`와 `db/*.sql`이 쓰이는지 확인해 사용처가 없으면 `scripts/ops/` 또는 삭제 | 낮음 | 참조 grep, `rag.verify`, 샘플 로더 실행 |
| 2 | `scripts/`를 `ops`/`eval`/`reports`로 분류. 영문 래퍼는 유지하고 한글 본체를 영문 이름으로 통일(문서·README 링크 일괄 갱신) | 중간(경로 참조) | 문서 링크 검사, `setup --check`, 래퍼 실행 |
| 3 | 루트 실행 파일을 `bin/`으로 이동하고, 루트에는 `README`의 "시작하기" 표 하나만 둔다. `ui/mockups/프로토타입_DB샘플연동.html`은 `ui/mockups/`로 이동 | 중간 | 각 `.cmd` 실행 확인 |
| 4 | `docs/` 루트 PDF·`진행보고`를 `docs/reports/`·`docs/api/`로 정리, `plan/` 초기 자료를 `plan/archive/`로 이동. `docs/README.md`를 기준 목차로 유지 | 낮음 | 링크 검사(`%20`·`<…>` 표기 처리 보정 필요) |
| 5 | 이름 충돌 해소: `src/search_client` → `src/search_client` | 중간(import 다수) | `pytest`, `mypy` |
| 6 | 대형 모듈 분리: `repository.py` → `repository/{base,memory,postgres,schema}.py`, `service.py` → 기능별(조회·답변·첨부·통계) 믹스인/모듈, `place_tool.py`를 파서·색인·MCP로 분리. **공개 API(`from src.complaints.service import ...`)는 `__init__`에서 그대로 재노출** | 높음 | 전체 테스트, 실서버 E2E |
| 7 | 가상환경을 하나로 통합할지 결정(`.venv`는 모델 실행용 Python 3.12, `.venv-web`은 웹용). 통합이 어려우면 문서에서 "무엇을 어디에 쓰는가"를 한 표로만 고정 | 중간 | `setup --check` |

## 4. 먼저 결정해 달라는 사항

1. 한글 파일명을 유지할지, 스크립트만 영문으로 통일할지(다른 OS·CI 호환성은 영문이 유리하고, 문서·사례 파일명은 한글 유지가 프로젝트 관행과 맞다).
2. 6단계(대형 모듈 분리)를 지금 할지, 기능 추가가 잠잠할 때로 미룰지.
3. `db/`의 샘플 JSON·SQL이 아직 필요한지.

## 5. 하지 않을 것

- `docs/cases/` 사례 파일의 이름과 번호는 바꾸지 않는다(외부 링크·색인 안정성).
- RAG 원본·색인과 업무 DB를 합치지 않는다(AGENTS.md 경계 유지).
- Docker 의존성을 추가하지 않는다.
