2026-10-30에는 [외부 LLM 호출 예제](../docs/harness/외부_LLM_API_호출.md)를 추가했다. API 접속·일반 대화 예제만 구현했으며 검색 근거 전달, 판정·FAQ 응답 검증, 모델 비교·선정과 민원 챗봇 연결은 후속 작업으로 유지한다.

## 현재 기준점

원본 두 JSON, 부서 정규화, PostgreSQL/pgvector, 한국어 BM25, RRF, 재정렬, 검색 CLI/API, 기본 테스트와 보고서가 있다. 작업 규칙·구조·데이터 계약·판정 초안·평가·운영 문서를 연결했고, 전체 문서 목차와 변경 이력으로 진입점을 정리했다.

다음 완료 대상은 **Jev 없이 LLM + RAG로 FAQ 답변 / 부서 추천 / 담당자 검토를 보여 주는 CLI 챗봇**이다. 이후 시연 웹은 **민원 게시판·작성 페이지와 민원을 주고받는 서버까지** 구현한다. Jev는 웹의 필수 선행 조건이 아니다. 시연 서비스의 등록·답변·검토 기록과 청주시 공식 접수·외부 부서 이관 연계를 구별한다. [웹·민원 서버 계획](시연_웹_게시판과_민원_서버_구현계획.md)

순서 1과 2의 준비는 함께 진행할 수 있다. 평가 라벨과 정책 계약 검증은 CLI 완료 전에 필요하다. 5번의 측정 준비는 2~4번 개발 중에도 진행한다. 후속 A와 B는 서로의 필수 선행 조건이 아니며 각각 기준 구성과 비교한다. 문서 초안만으로 특정 모델·운영 기준을 확정하지 않는다.

6-1~6-3의 일반 게시판·서버 준비는 AI 계층 개발과 함께 진행할 수 있다. 웹 완료는 6-5까지 등록→AI 검토→담당자 답변→시민 확인 흐름을 서버 저장 결과로 확인한 시점으로 한다. 세부 상태·API·권한 방식은 웹 계획의 구현 제안이며 아직 확정·구현되지 않았다.

## 분야별 작업과 추가 웹 요구

2026-10-27 사용자는 실제 게시판 목록·CRUD, AI 답변 표시·담당자 수정, 실시간 AI 작업 모니터를 요구했다. [통합 상세설계](민원_웹_MVP_상세설계와_분야별_작업계획.md)·[PDF](민원_웹_MVP_상세설계와_분야별_작업계획.pdf)에 UI 10개·백엔드 10개·AI 9개·DB 9개, 총 38개 작업의 구현 내용·완료 기준·연결 순서를 정리했다. UI는 화면·조작, 백엔드는 API·작업자·이벤트·운영, AI는 검색·판정·생성·평가, DB는 저장·무결성·복원으로 나눈다. 작업 식별자는 UI01~10·BE01~10·AI01~09·DB01~09이며 개인별 담당을 배정하지 않는다. 기존 검색 기반은 재사용·검증하고 웹·LLM 기능은 후속 구현한다. Flask·SSE·게시 정책은 여전히 제안이다.

## 우선 처리할 구체적 과제

**데이터:** 현재 업무분장이 미검증인 127개 부서를 모두 검증했다고 간주하지 않는다. 우선 시연 범위부터 공식 근거를 기록하고, 미래산업과 계열 10건·과거 안전정책과 17건의 대응은 건별로 검토한다. FAQ 현행성은 원문 해시·확인 일자·근거를 기록한 허용 목록부터 시작하고 내용 변경 시 다시 확인하도록 제안한다. 이번 계획 변경 자체는 원본 JSON 수정·DB 재구축·재임베딩 사유가 아니다.

**범용 LLM:** Qwen3.5-4B부터 판정·FAQ 생성을 시험하는 안을 제안하며 최종 선택은 미정이다. 같은 모델을 두 역할에 재사용하고 그 사이에 코드 정책 검사를 둔다. 9B 및 다른 계열은 자원·오류에 맞춰 비교한다. 정확한 저장소·리비전·라이선스·엔진·양자화를 고정하고 기존 검색 환경과 분리한다. LLM의 자기 보고 confidence를 정답 확률로 사용하지 않는다.

**Jev·학습:** OneJev/OpenJev/공식 Jev는 후속 비교 후보로 둔다. 이름이나 API 유사성으로 한국어 성능·점수 호환성을 가정하지 않는다. LoRA는 추가 학습 없는 기준 성능을 확보하고 데이터·검색·프롬프트를 보완한 뒤에도 반복되는 오류가 있을 때 검토한다.

**평가 하네스:** 현재 10개 검색 예제를 유지하며 별도의 LLM 판정·답변 평가 러너를 만든다. 특히 FAQ와 단어가 같지만 실제 조치를 요구하는 민원, 구별 관할, 데이터 밖의 민원, 조건 누락, 잘못된 구조화 출력과 시간 초과를 포함한다. 목표 오류율·지연·안내 비중은 기준 성능을 측정한 뒤 정하고 보류 평가셋으로 확인한다. 초기 모델 비교용 400문항은 제안이며 아직 작성되지 않았다.

**개발 자동화:** 가벼운 코드·격리 DB 검증부터 CI로 연결하고, 모델 다운로드·전체 임베딩·장시간 검색 평가는 별도 작업으로 분리한다. 현재 GitHub Actions는 구성되어 있지 않다. 유료 실행 자원 도입을 전제로 하지 않는다.

**운영 재현성:** 코드·원본 해시·모델·정책·평가셋 버전을 묶어 실행 기록을 남긴다. 현재는 호스트 PostgreSQL과 Python 가상환경·사용자 서비스를 사용하는 네이티브 방식이다. 공개 서비스 전환 전에는 배포 버전 고정, 접근 제어, 요청 제한, 백업 복원 연습을 별도 과제로 다룬다.
