# 하네스 보완과 MVP 실행 계획

[프로젝트 소개](../README.md) · [문서 목차](../docs/README.md) · [변경 이력](../CHANGELOG.md)

갱신 기준: 2026-10-25 UTC. **LLM + RAG를 먼저 구현하고 Jev는 추후 추가**한다는 사용자 결정에 맞춘 실행 과제다. 아래 미구현 항목의 완료나 모델 선택을 선언하는 문서는 아니다. 기본 작업 규칙은 [AGENTS.md](../AGENTS.md), 상세 계약은 [하네스 문서](../docs/harness/README.md)를 따른다. 이전 계획과의 차이는 [우선 구현계획](언어모델과_검색증강생성_우선_구현계획.md), 모델·학습 비교는 [제안서](모델_선정과_미세조정_제안.md)에 있다.

## 현재 기준점

원본 두 JSON, 부서 정규화, PostgreSQL/pgvector, 한국어 BM25, RRF, 재정렬, 검색 CLI/API, 기본 테스트와 보고서가 있다. 작업 규칙·구조·데이터 계약·판정 초안·평가·운영 문서를 연결했고, 전체 문서 목차와 변경 이력으로 진입점을 정리했다.

다음 완료 대상은 **Jev 없이 LLM + RAG로 FAQ 답변 / 부서 추천 / 담당자 검토를 보여 주는 CLI 챗봇**이다. 웹 목업은 그 다음이다. Jev는 기본 성능 확보 후 비교하며 웹 목업의 필수 선행 조건으로 두지 않는다. 실제 접수·이관 연계는 별도 범위로 남긴다.

## 실행 순서와 완료 조건

| 순서 | 작업 | 산출물·완료 조건 | 상태 |
| --- | --- | --- | --- |
| 1 | 기준 데이터·평가 라벨 준비 | 시연용 FAQ의 현행성·적용 조건, 부서 후보의 검증 상태, 한국어 개발/보류 평가셋 기록 | 미구현 |
| 2 | 범용 LLM 어댑터·프롬프트 | Jev 의존성 없이 한국어 판정 JSON과 조건부 FAQ 생성 호출, 스키마 검증·실패 처리 | 미구현 |
| 3 | 정책 검사·응대 조합 | 실제 조치와 안내 구분, 후보 ID·현행성 기록 대조, 같은 LLM으로 FAQ 생성·근거 검사 | 미구현 |
| 4 | CLI 챗봇 | LLM + RAG만으로 세 결과와 이유·출처 표시, 종료·오류 처리, 실제 이관과 시연 구분 | 미구현 |
| 5 | 기준 평가·관측 | 추가 학습 없는 LLM + RAG 비교, 오류율·안내 비중·전체 지연 기록, 개인정보 제외 | 미구현 |
| 6 | 웹 목업 | CLI와 같은 판정 로직 사용, 입력·대기·답변·추천·오류 상태 표시 | 미구현 |
| 후속 A | Jev 비교·추가 | 5번 이후 같은 근거·결과 계약으로 판정 대체/보완 효과 평가, 기본 경로 유지 | 후속 단계 |
| 후속 B | 필요 시 LoRA | 반복 오류·검수 데이터 확보 후 학습 전/후 비교와 회귀 검사 | 조건부 제안 |

순서 1과 2의 준비는 함께 진행할 수 있다. 평가 라벨과 정책 계약 검증은 CLI 완료 전에 필요하다. 5번의 측정 준비는 2~4번 개발 중에도 진행한다. 후속 A와 B는 서로의 필수 선행 조건이 아니며 각각 기준 구성과 비교한다. 문서 초안만으로 특정 모델·운영 기준을 확정하지 않는다.

## 우선 처리할 구체적 과제

**데이터:** 현재 업무분장이 미검증인 127개 부서를 모두 검증했다고 간주하지 않는다. 우선 시연 범위부터 공식 근거를 기록하고, 미래산업과 계열 10건·과거 안전정책과 17건의 대응은 건별로 검토한다. FAQ 현행성은 원문 해시·확인 일자·근거를 기록한 허용 목록부터 시작하고 내용 변경 시 다시 확인하도록 제안한다. 이번 계획 변경 자체는 원본 JSON 수정·DB 재구축·재임베딩 사유가 아니다.

**범용 LLM:** Qwen3.5-4B부터 판정·FAQ 생성을 시험하는 안을 제안하며 최종 선택은 미정이다. 같은 모델을 두 역할에 재사용하고 그 사이에 코드 정책 검사를 둔다. 9B 및 다른 계열은 자원·오류에 맞춰 비교한다. 정확한 저장소·리비전·라이선스·엔진·양자화를 고정하고 기존 검색 환경과 분리한다. LLM의 자기 보고 confidence를 정답 확률로 사용하지 않는다.

**Jev·학습:** OneJev/OpenJev/공식 Jev는 후속 비교 후보로 둔다. 이름이나 API 유사성으로 한국어 성능·점수 호환성을 가정하지 않는다. LoRA는 추가 학습 없는 기준 성능을 확보하고 데이터·검색·프롬프트를 보완한 뒤에도 반복되는 오류가 있을 때 검토한다.

**평가 하네스:** 현재 10개 검색 예제를 유지하며 별도의 LLM 판정·답변 평가 러너를 만든다. 특히 FAQ와 단어가 같지만 실제 조치를 요구하는 민원, 구별 관할, 데이터 밖의 민원, 조건 누락, 잘못된 구조화 출력과 시간 초과를 포함한다. 목표 오류율·지연·안내 비중은 기준 성능을 측정한 뒤 정하고 보류 평가셋으로 확인한다. 초기 모델 비교용 400문항은 제안이며 아직 작성되지 않았다.

**개발 자동화:** 가벼운 코드·격리 DB 검증부터 CI로 연결하고, 모델 다운로드·전체 임베딩·장시간 검색 평가는 별도 작업으로 분리한다. 현재 GitHub Actions는 구성되어 있지 않다. 유료 실행 자원 도입을 전제로 하지 않는다.

**운영 재현성:** 코드·원본 해시·모델·정책·평가셋 버전을 묶어 실행 기록을 남긴다. 현재 Compose는 코드 디렉터리를 읽기 전용으로 마운트하는 개발 방식이다. 공개 서비스 전환 전에는 배포 버전 고정, 접근 제어, 요청 제한, 백업 복원 연습을 별도 과제로 다룬다.

## 결정 기록

| 항목 | 상태 | 내용 |
| --- | --- | --- |
| 데이터 역할 | 확정·구현 | FAQ는 안내, 사례는 부서 추천, directory는 부서 검증 정보 |
| 검색 방식 | 확정·구현 | pgvector + Kiwi BM25 + RRF + 재정렬, 컬렉션별 검색 |
| 검색과 최종 판단 분리 | 확정·검색 계약 구현 | 현재 결과는 `requires_gate`; 후속 판단은 별도 |
| 초기 구성 | **2026-10-25 사용자 확정** | Jev 없는 LLM + RAG부터 구현; 이전 Jev 우선 제안 대체 |
| Jev 도입 순서 | **2026-10-25 사용자 확정** | 기본 기능 이후 확장; 구체 모델·적용 위치는 후속 평가 |
| 입력 언어 | 확정 | 한국어 직접 입력 우선, Papago는 추후 비교 |
| 모델 비용 | 선호 확정·모델 미선정 | 무료 로컬 LLM 우선 검토 |
| 시연 순서 | 확정 | CLI 챗봇 → 웹 목업 |
| 부서 구분 | 확정·구현 | 확인된 별칭 통합, 구별 동명 과 유지, 미확인 부서는 검토 |
| 판정 출력 스키마 | 설계 초안 | `faq_answer / department_suggestion / human_handoff`, 의도·근거·검토 상태를 코드에서 검증 |
| 초기 모델·호출 방식 | 제안·미선정 | Qwen3.5-4B부터 비교; 같은 LLM의 판정/생성 두 호출 |
| LoRA | 조건부 제안 | 학습 없이 시작하고 실패 분석·검수 데이터 확보 후 검토 |
| 운영 기준·시간 제한 | 미정 | 평가와 자원 측정 후 결정 |
| 실제 행정 이관 | 별도 범위 | 초기 MVP에서 완료된 이관으로 표시하지 않음 |

새 결정을 할 때는 날짜, 근거, 바뀌는 계약, 검증 결과를 이 기록과 해당 문서에 남긴다. 기존 방향을 바꾸지 않는 구현 세부 사항은 작업자가 정하고 기록한다. 모델·정책을 확정하는 데 사용자 선택이 필요한 항목만 구체적인 비교 결과와 함께 제시한다.
