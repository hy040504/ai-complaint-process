## 2. 배경·증상과 기대 동작

- 관찰한 사실과 영향: PostgreSQL 통일 이후에도 목차·실행 계획이 `complaint_app`을 미사용·SQLite로 적거나, README 다음 단계에 이미 된 업무 저장을 남겼다. 저장소는 요청마다 SQL 식별자를 다시 조합하고, 적재 캐시는 문서마다 SELECT를 보냈다. Swagger 진입 함수는 반환 설명이 없었다.
- 기대 동작 또는 요구사항: 한국어 Google 형식 docstring, 패치와 같은 현재 문서, README에서 두 스키마와 Swagger PDF가 바로 보이고, 중복 조회를 줄인다.
- 확인 근거와 시점: 2026-11-05 사용자 요청 「주석 점검, readme/docs 업데이트, readme 디자인 개선, 코드 최적화」.

## 3. 재현·확인 방법

- 비교한 기존 동작: `PostgresRepository`가 `sql.Identifier(self.schema)`를 메서드마다 만들었다. `ingest`가 캐시 미히트 후보마다 `embedding_cache`를 한 행씩 읽었다. `docs/README.md` 데이터 표는 `complaint_app.sql`을 「후속·미사용」이라고 했다.
- 판단 근거: 식별자 조합은 인스턴스 생성 때 한 번이면 충분하다. 캐시는 `text_hash = ANY(%s)`로 묶을 수 있다. 역사 사례의 SQLite 기록은 그대로 두고 현재 기준 문서만 고친다.

## 4. 원인 분석 또는 결정 근거

- 확인된 원인·근거: CASE-031~033은 동작·PDF에 집중했고 주석·현재 문서·중복 조회를 이 작업으로 넘겼다.
- 검토한 선택지와 결정 이유: 연결 풀은 넣지 않는다. 캐시 조회만 묶고, 스키마 적용은 저장소 생성 때 그대로 둔다.
