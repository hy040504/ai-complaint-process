## 2. 확인된 문제와 근거

[data-integrity.json](../../rag/reports/data-integrity.json)은 부서 디렉터리 127개 모두의 업무분장이 미검증이며, 현행 담당 부서를 재확인해야 하는 사례가 27건임을 기록합니다. 이는 현재 DB를 새로 조회한 수치가 아니라 해당 실행의 스냅샷입니다.

- `duty_description=null`, `duty_status="unverified"`이며 이름에서 추출한 구 정보는 실제 업무 관할을 확정한 값이 아닙니다.
- 미래산업과 계열 10건과 과거 안전정책과 17건은 업무별 현행 부서 대응이 필요합니다.
- 대중교통과와 건설교통국 대중교통과는 통합했지만, 구가 다른 건설과는 구별해야 합니다.

필드 정의와 원래 표기의 보존 범위는 [데이터 사전](../../db/README.md), 후보 처리 방식은 [RAG 문서](../../rag/README.md#부서-검증의-범위)에 있습니다.

## 3. 원인과 현재 대응

공개 사례의 담당 부서 표기만으로 현행 공식 업무분장과 개별 업무의 관할을 확보할 수 없습니다. 과거 조직명과 여러 업무가 섞인 사례를 이름만으로 한 부서에 매핑하면 잘못된 추천을 만들 수 있습니다.

[입력 처리](../../rag/data.py)는 `review_required` 사례의 현재 부서를 `null`로 유지하고, [검색 코드](../../rag/search.py)는 해당 사례를 부서 후보 집계에서 제외합니다. 모든 부서의 `automatic_routing_ready`와 후보의 `automatic_transfer`는 현재 `false`입니다. 이 보호 조치가 업무·관할 검증 완료를 뜻하지 않습니다.

## 4. 확인 방법과 후속 조치

1. [운영 절차](../harness/runbook.md)의 조회 방법으로 작업 시점의 건수·검증 상태를 확인합니다.
2. 시연 대상 업무부터 현행 조직·업무분장·관할의 공식 출처와 확인 일자를 기록합니다.
3. 27개 사례는 제목·요지·처리 맥락을 업무별로 검토하고, 근거가 부족하면 미확인 상태를 유지합니다.
4. 부서 이름과 내부 ID의 변경·기존 검증 값 보존 여부를 검토하고, 변경한 데이터에 맞는 무결성·추천 회귀 확인을 수행합니다.

이 사례를 작성하면서 부서 정보를 새로 검증하거나 데이터를 수정하지 않았습니다. 코드·자료 대조로 기존 미검증 상태를 등록했으며 해결 검증은 미실행입니다.

## 5. 완료 조건과 복구

선택한 처리 범위에 대해 공식 업무분장·관할·과거 부서 대응 근거가 기록되고, 검증 상태와 사례 FK·후보 제외 규칙이 일치해야 합니다. 일부 업무만 검증했다면 부분 완료 범위를 명시하고 나머지를 별도 추적합니다. 실제 자동 이관 허용은 [판정 정책](../harness/decision-policy.md)의 후속 구현·평가와 별도 연동이 필요합니다.

변경 전 원본과 부서 검증 정보를 백업하고, 잘못된 매핑이 확인되면 해당 후보를 미확인으로 되돌리는 절차를 [운영 절차](../harness/runbook.md)에 따라 수행합니다. 다음 작업은 [실행 계획](../../plan/harness-roadmap.md)의 기준 데이터 준비와 연결합니다.
