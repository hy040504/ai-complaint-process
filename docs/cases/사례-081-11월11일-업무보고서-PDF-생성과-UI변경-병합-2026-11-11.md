## 2. 배경·증상과 기대 동작

- 관찰한 사실과 영향:
  - 11월 11일에는 대규모 신규 기능 추가보다는 어제까지 구축된 백엔드 자동 기동 및 네이버 지도 장소 추적 MCP(`lookup_navermap_place`)를 바탕으로 민원 유형별 LLM 응답 품질, 환각 여부, 장소 기반 부서 매칭 집중 테스트를 수행함.
  - 협업 팀원인 기민 님이 11월 11일 기준으로 담당자 목록 접수 경과일 표시, 편집기 글자 수 카운터, 자주 쓰는 문구 삽입 단추, Ctrl+S 단축키, 처리 이력 접힘 통일 등을 반영한 3페이지 분량의 "UI 변경 보고서" PDF를 전달함.
- 기대 동작 또는 요구사항:
  - 1페이지: `업무보고_20261110.pdf`의 기존 양식(테이블 레이아웃, 연승현 톤, 팀원 '기민 님' 호칭)을 정확히 계승하여 11월 11일의 LLM 테스트 및 기민 님 신규 UI 변경 사항 점검 결과를 딱 1페이지로 완결성 있게 작성.
  - 2~4페이지: 기민 님이 작성한 `UI_변경_2026-11-11.pdf`의 원본 3페이지를 서식과 이미지 손실 없이 그대로 병합하여 총 4페이지 PDF 발행.
  - 카카오톡 다운로드 폴더 및 프로젝트 내부 `docs/` 폴더에 동시 저장.

## 3. 재현·확인 방법

- PDF 생성 스크립트 실행:
  ```powershell
  .venv-web\Scripts\python.exe scripts/업무보고_20261111_pdf_생성.py
  ```
- 생성된 PDF의 총 페이지 수 및 텍스트 검증:
  - 총 4페이지 (1페이지: 메인 표, 2~4페이지: UI 변경 보고서 원본).
  - 텍스트 추출 검사로 누락이나 잘림 없이 1페이지 표가 단일 페이지에 온전히 렌더링되는지 확인.

## 4. 원인 분석 또는 결정 근거

- 헤드리스 크롬과 pypdf의 결합:
  - HTML/CSS로 구성된 1페이지 메인 표를 헤드리스 크롬의 인쇄 엔진으로 정밀 렌더링(`--print-to-pdf`, `--no-pdf-header-footer`)하여 텍스트 흐름과 표 외곽선 무결성을 확보함.
  - 이후 `pypdf.PdfWriter`를 통해 1페이지 PDF와 기민 님의 11/11 원본 PDF 3페이지를 스트림 손실 없이 병합하여 총 4페이지로 완성.
- 경로 탐색 폴백(Fallback) 구조:
  - 로컬 카카오톡 다운로드 폴더에서 파일이 이동되더라도 스크립트가 중단되지 않도록, 프로젝트 내부 `docs/UI_변경_2026-11-11.pdf`를 보관하고 순차 탐색하도록 방어 로직 구현.
