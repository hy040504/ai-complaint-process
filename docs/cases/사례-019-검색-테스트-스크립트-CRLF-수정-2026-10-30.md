## 2. 배경·증상과 기대 동작

- 관찰한 사실과 영향: Windows에서 `bash rag/test_search.sh`를 실행하면 `set: pipefail: invalid option name`, `native-env.sh: No such file or directory`, `RAG_ROOT: unbound variable`로 즉시 실패했다. 파일은 UTF-8이며 내용은 정상이었고, 작업 트리만 CRLF였다.
- 기대 동작 또는 요구사항: `bash rag/test_search.sh`가 메뉴·`--help`·`--status`를 실행한다. 검색 API가 꺼져 있으면 연결 오류를 표시하고 종료한다.
- 확인 근거와 시점: 2026-10-30, 작업 트리 `rag/test_search.sh`와 `scripts/*.sh`가 CRLF 137줄, Git 저장 형식은 `i/lf w/crlf`.

## 3. 재현·확인 방법

- 재현 환경·선행 조건: Windows 작업 트리, Git `core.autocrlf=true`, WSL bash.
- 개인정보를 제거한 입력, 단계, 실제 결과: WSL에서 `bash rag/test_search.sh --help` → `set: pipefail: invalid option name`. PowerShell에서 Windows 경로를 `bash`에 넘기면 한글 경로 깨짐과 `No such file or directory`.

## 4. 원인 분석 또는 결정 근거

- 확인된 원인·근거: Git이 체크아웃 시 LF를 CRLF로 바꿨다. GNU bash는 `set -uo pipefail\r`을 잘못된 옵션으로 읽고, `source .../native-env.sh\r`를 다른 파일로 찾는다.
- 검토한 선택지와 결정 이유: 스크립트 내용을 CRLF에 맞춰 고치는 대신, 셸 스크립트는 LF로 유지한다. `.gitattributes`의 `*.sh text eol=lf`가 `core.autocrlf`보다 우선한다.

- 검색 API가 이 Windows 호스트에서 실행 중이지 않아 실제 FAQ·사례 검색은 확인하지 않았다.
- PowerShell `bash C:\...test_search.sh`는 WSL이 Windows 경로를 받지 못하므로, WSL에서 저장소 루트로 이동한 뒤 `bash rag/test_search.sh`를 사용한다.

## 7. 완료 조건·후속 작업·복구

- 완료로 판단할 조건과 충족 근거: WSL에서 문법 검사와 `--help`가 성공하고, `--status`가 CRLF 오류 없이 API 클라이언트를 호출한다.
- 남은 작업: 검색 서비스가 있는 환경에서 메뉴·실제 검색 재확인, 원격 반영은 커밋·push 후.
- 되돌리기: `.gitattributes`와 스크립트 줄 끝을 이전 상태로 되돌린다.
