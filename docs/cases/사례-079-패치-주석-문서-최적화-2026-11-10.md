## 2. 배경·증상과 기대 동작

- 관찰한 사실과 영향:
  - CASE-078에서 신규 추가된 `src/llm/place_tool.py`와 `src/llm/rag_mcp.py`의 함수 및 모듈 주석이 표준 규격에 맞게 작성되었는지 전수 점검이 필요함.
  - 검색어에 연속 공백이나 탭이 섞여 있을 때 동일 장소임에도 캐시 미스가 발생할 수 있고, 캐시 상한(256건) 도달 시 전체를 지우는 방식보다 오래된 절반을 삭제하는 FIFO 큐 방식이 캐시 효율성이 높음.
  - 과거 SQLite 사용 시절 남겨진 레거시 `db/` 디렉터리가 남아 있어 개발자에게 혼선을 줄 수 있음.
- 기대 동작 또는 요구사항:
  - 모든 모듈·함수·테스트의 Google 형식 한국어 docstring 및 매개변수/반환값 설명을 완벽히 맞춤.
  - 검색어 공백 정규화(`" ".join(query.split())`) 및 FIFO 캐시 퇴출 최적화 적용.
  - 레거시 `db/` 디렉터리 안전하게 삭제 및 문서 갱신.
  - 루트 `README.md`의 머메이드 다이어그램 및 배지 디자인을 시각적으로 개편하여 신규 MCP 흐름을 명확히 표현.
  - 단위 테스트 및 회귀 테스트 100% 통과 검증 후 한국어 커밋 메시지로 GitHub 푸시.

## 4. 원인 분석 또는 결정 근거

- 캐시 최적화:
  - `"창신초   정문"`과 `"창신초 정문"`이 서로 다른 키로 인식되지 않도록 검색어 정규화를 거침.
  - 캐시가 가득 찼을 때 단순 `clear()` 대신 상위 50%의 오래된 항목만 선별 삭제하여 캐시 적중률 유지.
- 문서 및 다이어그램:
  - 응대 검사기 및 Codex 파이프라인에서 MCP stdio 서버(`rag_mcp`)가 `search_complaint_rag`와 `lookup_navermap_place` 두 도구를 처리하는 양방향 구조를 Mermaid 다이어그램에 반영하여 전체 구조 이해도를 높임.
