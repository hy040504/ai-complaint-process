## 2. 배경·증상과 기대 동작

- **관찰한 사실과 영향:**
  1. 추출한 응대 검사기(`:5010` `src/lab_web`)에는 엔진 선택(`exaone_api`·`codex_cli`·`openai_api`·`.env` 기본 및 미설정 잠금), 청주시 4대 구·98개 읍·면·동 선택, 본문 지명·네이버 지도(`inferredPlace`) 장소 추적, `분야:` 제외 검색 질의, 엔진별 보낸 데이터(JSON ↑)·프롬프트(↓) 표시가 구현되어 있었으나, 본 민원 웹(`:5000`)과 `#/lab`에는 이식이 누락되어 있었습니다.
  2. `:5000` `AssistInput.rerank`가 기본 `True`여서 Windows 호스트에서 HuggingFace SSL(`CERTIFICATE_VERIFY_FAILED`)로 검색 API 호출 시 503 오류가 발생할 수 있었습니다.
  3. 민원 등록·수정·담당자 AI 작업 실행 시 실제 AI 연결(`iter_web_assist`) 없이 시간 경과 기반 단계 시연(`advance_jobs`)만 실행되어 `aiAssist`·부서 후보·`PREFIX-03` 초안·`PREFIX-04` 순화 결과가 저장되지 않았습니다.
- **기대 동작 또는 요구사항:**
  - 시민 민원 등록/수정 및 담당자 작업 실행(`POST /api/v1/complaints/<id>/jobs`)에서 선택 가능한 LLM 공급자로 실제 RAG+LLM 파이프라인을 백그라운드로 비동기 실행합니다.
  - 시민 응답(`PublicComplaint`·`PublicWorkspace`)에서는 `aiAssist`·`aiOriginal`·`aiCandidate`·`draft`·`versions`·`job` 및 미게시 답변을 완전히 차단합니다.
  - 담당자가 이미 작성·수정한 초안(`draft` 또는 `versions`에 `초안 저장`·`게시` 존재)은 이후 AI 재실행이나 타 공급자 재실행으로 절대 덮어쓰지 않고 `aiCandidate`와 `aiAssist`만 갱신하며, 취소·수정으로 무효화된 지연 AI 결과는 폐기합니다.
  - `#/lab`도 `:5010`과 동일한 엔진 선택/잠금, 읍·면·동 선택, 장소 추적, 데이터(JSON ↑)·프롬프트(↓) 트레이스, `rerank=false` 기본값을 사용합니다.

## 3. 재현·확인 방법

- **실서버 E2E 검증 조건:** 로컬 `:8007` (`python -m rag serve` · FAQ 94건 / 사례 5,015건 / 부서 127개) + 로컬 `:5000` (`python -m src`, `COMPLAINT_APP_SCHEMA=complaint_app_e2e`) + PostgreSQL `complaints_native`.
- **확인 항목:**
  1. `/api/v1/assist`·`/api/v1/assist/stream`에 `exaone_api`(`k-exaone_v2.5`, `district="오송읍"`), `codex_cli`(`gpt-6-luna`), 미설정 `openai_api`, 잘못된 자치구(`청주시` 422) 호출.
  2. 민원 등록(`POST /api/v1/complaints`) → 1.5초 폴링 중 `version` 고정 및 진행 단계 확인 → 담당자 `aiAssist`/`aiOriginal`/`draft` 확인 → 시민 비공개 경계 확인 → 담당자 초안 수정 후 `exaone_api` 재실행(초안·최초 `aiOriginal` 보존) → 게시(`origin="ai_edited"`) → 게시 후 시민 비공개 경계 재확인 → `openai_api` 실행 시 안전 처리(`llm_unavailable`)·기존 초안 보존 확인.

## 4. 원인 분석 또는 결정 근거

- **비동기 워커 + 메모리 라이브 진행(`_live_jobs`):** AI 분석(특히 `k-exaone_v2.5`의 `decision` + `staff_draft` 다단계 추론은 실측 시 약 150~245초 소요) 중 매 진행 단계마다 DB `version`을 증가시키면 편집 중인 담당자가 `409 version_conflict`를 겪게 됩니다. 이에 `ComplaintService`는 백그라운드 데몬 스레드(`_run_ai_worker`)가 진행 이벤트를 `_live_jobs` 메모리에만 기록하고 조회 시 `_enrich_live`로 병합하며, 완료/실패 시에만 `attempt`·`context_version`·`job.status == "running"` 조건부 낙관적 커밋(`_commit_with_retry`)을 수행하도록 설계했습니다.
- **자치구 DB 제약과 지명 자동 추론 분리:** `complaint_app.complaints`의 DB `CHECK` 제약(`상당구`, `서원구`, `흥덕구`, `청원구`, `모름`)은 그대로 유지해 스키마 호환성을 지키고, 민원 등록·수정 시 `모름`을 `None`으로 넘겨 `src.assist`가 본문 지명·네이버 지도로 자치구·장소(`ai_assist.district`, `ai_assist.inferred_place`)를 자동 추론하도록 분리했습니다. 반면 `#/lab`의 `AssistInput.district`는 `normalize_district()`로 4개 구 + 98개 읍·면·동을 모두 허용합니다.
- **공유 메타데이터 분리:** 엔진 라벨·배지·사유·읍·면·동 `<optgroup>` 생성을 `ui/src/llm-meta.js`로 통합해 `ui/src/lab.js`, `ui/src/staff.js`, `ui/src/app.js` 간 중복을 제거했습니다. 백엔드는 `Provider` 및 `normalize_optional_text`를 `src/llm/settings.py`로 단일화하고 `AssistResponse`·`ProviderStatus`를 `src/complaints/models.py`에서 `src/lab_web/models.py`로 재사용했습니다.
