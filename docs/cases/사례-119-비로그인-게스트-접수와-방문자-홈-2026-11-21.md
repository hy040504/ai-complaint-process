## 1. 증상과 요구

시연 로그인을 끈 서버에서는 비로그인 방문자가 "계정 로그인이 필요합니다"에서 막혀 홈조차 볼 수 없었다. 요구는 (1) 로그인하지 않아도 시민 사이트 홈이 보이고, (2) 게스트처럼 로그인 없이 민원을 보낼 수 있어야 하며, (3) 시민 로그인 화면에 같은 의미의 버튼이 두 개(탭 "민원인 로그인"과 제출 "민원인 로그인")라 부자연스러우므로 단순히 "로그인"이 낫다는 것이었다.

## 2. 설계 결정

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 게스트 신원 | DB 계정 없이 **서명 세션**의 `guest-<무작위 128비트>`(`auth_mode=guest`, `Actor.guest=true`) | 무료·무상태. PostgreSQL은 `users`에 없는 작성자 ID를 NULL FK로 안전하게 처리하고 작성자는 payload에 남음 |
| 세션 시작 시점 | 페이지 방문이 아니라 **접수·AI 도우미 사용 순간**에 자동 시작(`POST /api/v1/auth/guest`) | 홈을 열기만 해도 서버 상태를 만들지 않음 |
| 공개 범위 | ~~게스트 접수는 비공개로 강제~~ → **2026-11-22 정책 변경: 게스트 접수는 공개로 강제**(서버가 덮어씀) | 당초에는 스팸 노출 방지를 위해 비공개였으나, 사용자 결정으로 민원 게시판에 공개한다. 남용은 게스트당 5건·IP당 시간당 10회 제한으로 막는다 |
| 남용 방지 | 게스트 세션 발급 IP당 시간당 10회, 접수 IP당 시간당 10회, 게스트당 최대 5건(`429 guest_limit`) | 공개 터널에서 열린 입구이므로 |
| 이어쓰기 | 같은 브라우저 세션에서 조회·문의·첨부. **로그인·가입하면 게스트 민원이 그 계정으로 옮겨짐**(이력 기록) | 별도 조회 코드 없이 단순하게 |
| 챗봇 | 게스트 대화는 저장하지 않음(비로그인 임시 대화와 동일) | 개인 대화 영속 저장은 실계정만 |

## 3. 조치 내용

| 영역 | 변경 |
| --- | --- |
| 모델·인증 | `AuthMode`에 `guest`, `Actor.guest`. `AuthService.create_guest`·`resolve_session_actor`(ID 형식·역할 검증, 위조 거부), `SlidingWindowLimiter` |
| API | `POST /api/v1/auth/guest`(시민 사이트 전용, 이미 시민 세션이면 그대로 반환, 담당자 사이트는 `403 wrong_site`), 접수 시 게스트 IP 제한, 로그인·가입 시 `claim_guest_complaints` |
| 서비스 | 게스트 접수 공개 강제(2026-11-22 변경, 당초 비공개)·5건 한도, 게스트 챗봇 영속 저장 제외, 게스트 민원의 계정 이전(낙관적 잠금·`complaint.updated` 이벤트) |
| 화면 | 비로그인 방문자도 홈·민원 작성·AI 도우미·소식·서비스·이용 안내를 봄. "나의 민원·게시판·알림·내 정보·상세"는 로그인·게스트 접수 안내로 대체. 홈 우측 "로그인 없이 시작해요" 카드, 작성 폼은 공개 고정 안내(2026-11-22 변경, 당초 비공개), 접수 후 게스트 안내 배너 |
| 로그인 모달 | 탭이 하나뿐이면 탭 막대를 그리지 않고 제출 버튼은 **"로그인"**, 가입은 "가입하고 시작하기", "계정 만들기". 기본 계정 안내 문구 제거. 헤더 버튼은 게스트에게도 "로그인". 실계정이 아닐 때 DEMO 표지는 시연 계정(`demo`)에만 표시 |

## 5. 남은 한계

- 게스트는 쿠키를 잃으면(다른 기기·브라우저 삭제) 민원을 다시 볼 수 없다. 조회 코드(민원번호+비밀번호) 방식은 미구현이다.
- CAPTCHA가 없어 IP 제한만으로 자동화 남용을 막는다. Cloudflare 뒤에서는 원본 IP 판별이 `X-Forwarded-For`에 의존한다.
- 게스트 민원은 담당자 화면에 게스트 표시가 따로 없다(작성자 ID `guest-…`).
