## 2. 배경·증상과 기대 동작

- 관찰한 사실과 영향: 검색은 PostgreSQL `complaint_rag`이고, 시연 웹은 `db/app/complaints.sqlite3`, 적재 벡터 캐시는 `.rag-cache/embeddings.sqlite3`였다.
- 기대 동작 또는 요구사항: SQLite 파일을 쓰지 않고 같은 PostgreSQL 서버의 스키마로 통일한다. 검색 색인과 민원 행은 섞지 않는다.
- 확인 근거와 시점: 2026-11-05 사용자 요청.

## 3. 재현·확인 방법

- 비교한 기존 동작: Flask `SQLiteRepository`가 payload TEXT와 idempotency를 파일에 저장했다.
- 판단 근거: 현재 Flask 계약은 민원 Pydantic 문서를 통째로 보존한다. 7테이블 정규화 초안은 `plan/db 설계 1차`에 두고, 구현은 `complaint_app.complaints.payload` jsonb로 옮긴다.

## 4. 원인 분석 또는 결정 근거

- 확인된 원인·근거: 업무 데이터와 검색 지식을 한 파일에 넣으면 RAG 재적재와 민원 CRUD가 섞인다. 엔진만 PostgreSQL로 맞추고 스키마는 둘로 나눈다.
- 검토한 선택지와 결정 이유: 7테이블 정규화는 서비스·API를 다시 짜야 한다. 이번 작업은 저장 엔진 통일이다. 단위 테스트는 PostgreSQL 없이 메모리 저장소를 쓰고, 실제 SQL은 `RUN_PG_TESTS=1`에서 확인한다.

## 5. 조치와 변경 내용

| 파일·계약 | 변경 내용 | 구현·반영 상태 |
| --- | --- | --- |
| `src/complaints/repository.py` | `PostgresRepository` + 테스트용 `MemoryRepository`. SQLite 제거 | 적용 |
| `db/schema/complaint_app.sql` | jsonb `complaints`·`idempotency`. DROP CASCADE 없음 | 적용 |
| `rag/ingest.py` · `complaint_rag.sql` | 벡터 체크포인트를 `embedding_cache` 테이블로 이동 | 적용 |
| `/api/v1/health` `storage` | `postgresql` 또는 `memory` | 적용 |

시연 서버는 `COMPLAINT_STORE=postgresql`(기본)만 허용한다. 연결은 `COMPLAINT_DATABASE_URL` 또는 `PGHOST`/`PGDATABASE` 등 libpq 환경변수다. 스키마 기본값은 `complaint_app`이다.

- 기존 `complaints.sqlite3`를 자동 이관하지 않는다. 필요하면 시연 글을 다시 등록하거나 `seed-demo`를 쓴다.
- 7테이블 정규화 스키마·SSE·민원 CRUD AI는 후속이다.

## 7. 완료 조건·후속 작업·복구

- 완료: 시연 웹과 임베딩 체크포인트가 SQLite 파일에 의존하지 않고, 검색은 `complaint_rag`, 민원은 `complaint_app`이다.
- 남은 작업: 7테이블 정규화가 필요하면 별도 이관. SQLite 잔여 삭제는 [CASE-041](사례-041-잔여-SQLite-삭제-2026-11-05.md).
- 되돌림: 이전 `SQLiteRepository`와 `db/app/complaints.sqlite3` 경로. 검색 원본 JSON은 대상이 아니다.
