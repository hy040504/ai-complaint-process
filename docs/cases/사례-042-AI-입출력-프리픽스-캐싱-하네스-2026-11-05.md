## 2. 배경·증상과 기대 동작

- 관찰한 사실과 영향: 기존 `docs/harness/decision-policy.md`와 `src/assist/constants.py`에는 기본적인 3갈래 판정 규칙만 요약되어 있었고, 두 원본 기획서 분석 문서(`VoteLab_AI민원_상세기획안_상세분석.md`, `민원AI_계획서_상세분석.md`)에 담긴 긴급·처분성·특이민원 순화·개인정보 마스킹·시민/내부 공개 분리 원칙과 추후 **프리픽스 캐싱(Prefix Caching)**을 위한 고정 시스템 프롬프트 설계 기준이 하네스 문서로 정리되어 있지 않았다.
- 기대 동작 또는 요구사항: 프로젝트 현재 구현 경계와 두 기획서의 원칙을 통합하여, AI에게 정보를 보내고 응답을 받을 때의 지침사항과 프리픽스 캐싱 최적화용 시스템 프롬프트 명세를 `docs/harness/`에 체계화한다.
- 확인 근거와 시점: 2026-11-05 사용자 요청.

## 3. 재현·확인 방법

- 비교한 기존 동작: `src/assist/constants.py`의 `DECISION_SYSTEM`·`ANSWER_SYSTEM`, `src/assist/policy.py`의 `decision_prompt`·`validate_decision`, `src/rag/evidence.py`의 `compact_faq`·`compact_case`, `src/llm/complete.py`의 공급자별 호출 방식을 대조했다.
- 판단 근거: 프리픽스 캐싱이 작동하려면 시스템 프롬프트 앞부분(Static Prefix)에 동적 변수(시각, 요청 ID, 관할 구, 검색 후보 등)가 일절 섞이지 않아야 하며, 모든 작업이 공통 최상위 헌법 프리픽스(`PREFIX-00`)를 공유하고 가변 데이터는 `user` 메시지 JSON(Dynamic Suffix)으로만 전달해야 한다.

## 4. 원인 분석 또는 결정 근거

- 확인된 원인·근거: 기획서 원안의 전체 기능(TAXO 자동 배정, 특이민원 8대 신호, 담당자 7단계 초안 등)과 현재 로컬 MVP 구현(`src/assist`의 Jev 없는 LLM + RAG 2단계 호출)을 구분하지 않으면 구현 상태 오해나 프롬프트 비대화가 발생할 수 있다.
- 검토한 선택지와 결정 이유: 단일 문서에 모든 내용을 넣는 대신 역할별로 ① 입출력·검증 총괄 계약(`AI_정보전달과_응답_하네스.md`), ② 프리픽스 캐싱 구조 및 복사 가능한 계층별 시스템 프롬프트 원문(`시스템_프롬프트와_프리픽스_캐싱_지침.md`), ③ 개인정보·긴급·처분성·특이민원·공개 범위 가드레일(`AI_안전_보안_가드레일.md`)의 세 문서로 나누어 관리성과 재사용성을 높였다.
