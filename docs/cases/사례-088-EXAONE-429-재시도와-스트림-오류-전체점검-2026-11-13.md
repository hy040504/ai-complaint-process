## 2. 배경·증상과 기대 동작

- **관찰한 사실과 영향:**
  1. **EXAONE 429 연쇄 실패 및 `invalid_model_output` 오표기 (`src/assist/pipeline.py`, `src/rag/http.py`):** 실환경 EXAONE 호출 중 서버 측 동시 요청 폭주(`"service is busy, too many concurrent requests(600)"`, `rate_limit_exceeded`) 또는 초당 한도(`x-second-rate-limit: 1`)로 HTTP 429가 발생하면 `http_json`이 `retry-after-ms`/`retry-after` 백오프 없이 즉시 실패했습니다. 게다가 `pipeline.py`가 API 호출 실패를 `invalid_model_output`으로 처리한 뒤 `outcome != "faq_answer"` 분기를 그대로 타서 `sanitize`/`staff_draft`를 곧장 추가 호출했고, 결과의 `정책 검사`에 동일한 `API 429: ...` 오류가 **두 번 연속** 표시되었습니다.
  2. **`EXAONE_URL`·`EXAONE_MODEL` 환경변수 미연결 (`src/llm/settings.py`):** `src/README.md`에는 `EXAONE_URL`·`EXAONE_MODEL`이 문서화되어 있었으나 `_LLM_ENV_KEYS`와 `settings_for_provider("exaone_api")`에 빠져 있었고, 대신 `COMPLAINT_LLM_URL`을 읽어 타 공급자용 호환 URL이 `.env`에 있을 때 EXAONE 요청이 오발신될 수 있었습니다.
  3. **NDJSON 마지막 줄 유실 및 422·스트림 중단 후 중복 요청 (`src/lab_web/static/app.js`, `ui/src/lab.js`):** 스트림 EOF(`done === true`) 시 `decoder.decode()`와 `buffer` 잔여 줄을 소비하지 않아 마지막 청크에 개행이 없으면 `done` 이벤트를 놓쳤으며, 422 검증 오류·`error` 이벤트·`progress` 수신 후 실패 시에도 `/complaints`·`/assist` 비스트림 경로로 다시 요청해 이중 LLM 호출이나 두 번 실패를 유발했습니다. `showResult` 또한 `payload.provider`를 직접 참조해 방어가 약했습니다.
  4. **공급자 키 누락 메시지 불일치 (`src/assist/pipeline.py`):** 명시적 `provider` 선택 시 키/실행파일 누락 사유가 구형 `openai_api·codex_cli` 문구로만 나갔고, HTTP `TimeoutError`도 영문 원문(`The read operation timed out`) 그대로 노출되었습니다.
- **기대 동작:** 일시적인 429에는 EXAONE 공식 Rate Limits 헤더(`retry-after-ms`, `retry-after`, `x-day-rate-limit-remaining`)를 반영해 예의 있게 재시도하고, 판정 API 자체가 실패하면 `llm_unavailable`로 조기 종료하며, 스트림 끝 줄·오류 분기와 `EXAONE_URL`/`EXAONE_MODEL` 격리가 정확히 동작해야 합니다.

## 3. 원인 분석 및 결정 근거

- **EXAONE API 공식 Rate Limit 정책 (`docs.exaone.ai`):** K-EXAONE 2.5 무료 API는 `x-second-rate-limit`(예: 초당 1건), `x-minute-rate-limit`, `x-day-rate-limit` 및 서버 전체 동시성 제한(예: 600 동시 요청)을 적용하며, 429 응답 시 `retry-after`, `retry-after-ms`, `x-day-rate-limit-remaining` 헤더를 반환할 수 있습니다. (참고: EXAONE 마이 프로필에서 서비스 개선 데이터 활용 동의 시 일일 한도 상향이 가능하나, 공용 서버 혼잡·초당 한도에는 클라이언트 백오프와 연쇄 호출 억제가 필수입니다.)
- **계층 분리 유지:** `src/llm/complete.py` 테스트 mock 시그니처(`http_json(url, payload, headers)` 3인자)를 깨지 않기 위해 429 재시도와 `TimeoutError` 한국어 변환은 `src/rag/http.py` 내부 기본 키워드 인자(`max_429_retries: int = 2`)로 구현했습니다.
- **이중 실패·과부하 방지:** `pipeline.py`에서 `chat(...)` 호출 자체의 예외(`API 4xx/5xx`, 시간 초과, 연결 실패, Codex 실패)를 `parse_json_object`/`validate_decision` 검증 실패와 분리해, 호출 자체가 실패한 경우 `reason_code="llm_unavailable"`로 두고 후속 `sanitize`·`staff_draft`를 건너뛰도록 했습니다.
