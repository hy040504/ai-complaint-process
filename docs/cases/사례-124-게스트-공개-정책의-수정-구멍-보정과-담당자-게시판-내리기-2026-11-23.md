## 1. 문제

게스트 민원을 게시판 **공개로 고정**(2026-11-22)한 뒤 두 가지가 비어 있었다.

| # | 문제 | 확인 방법 |
| --- | --- | --- |
| 1 | **수정으로 정책을 우회할 수 있었다.** 공개 고정은 접수(`create`) 때만 적용되고, 본인 수정(`update`)은 요청의 `visibility`를 그대로 저장했다. 게스트가 접수 뒤 수정으로 비공개로 바꿀 수 있었다(이전 "비공개 고정" 때는 반대로 공개로 바꾸는 같은 구멍) | 코드(`service.update`) 확인, 테스트로 재현 |
| 2 | **담당자가 게시판 글을 내릴 방법이 없었다.** 담당자 작업은 검토·배정·초안·게시·철회·재시도·취소뿐이었다. 공개된 게스트 글에 개인정보나 스팸이 올라와도 막을 수단이 없었다 | 담당자 작업 목록(`Operation`) 확인 |

## 2. 결정

- 게스트의 공개 범위는 **접수 때만** 정한다. 수정으로는 바꾸지 못한다.
- 담당자에게 **공개 범위 조정**(내리기·다시 공개)을 준다. 사유를 필수로 받아 이력에 남긴다.
- 담당자가 내린 글을 작성자가 **수정으로 다시 공개하지 못하게** 한다(게스트·로그인 민원인 모두).
- 반대로 작성자가 직접 비공개로 정한 민원은 담당자가 **공개로 돌리지 못하게** 한다(사생활 보호). 담당자는 "자신이 내린 것만" 되돌릴 수 있다.
- 내림 여부는 DB 열을 새로 만들지 않고 **처리 이력의 마지막 조정**(`게시판에서 내림` / `게시판에 다시 공개`)으로 판별한다. 스키마 변경 없이 적용하기 위해서다.

## 3. 구현

| 영역 | 변경 |
| --- | --- |
| 모델 | `VisibilityInput`(기대 버전·`visibility`·사유) |
| 서비스 | 작업 `visibility`(담당자 전용·부서 범위 검사 포함), `hidden_by_staff()`, `update`의 게스트 고정·내린 글 재공개 거부(`409 hidden_by_staff`), 이미 비공개 내림 거부(`409 already_private`), 작성자 비공개 공개전환 거부(`409 not_hidden_by_staff`) |
| API | `PUT /api/v1/complaints/{id}/visibility`(담당자) |
| 화면 | 담당자 민원 상세 "처리 프로세스" 머리에 현재 공개 상태와 버튼: 공개 글은 **게시판에서 내리기**, 내린 글은 **게시판에 다시 공개**, 작성자가 비공개로 정한 글·철회된 글에는 버튼 없음. 사유 입력 모달 |
| 이력 | 담당자 조정은 시민에게 보이지 않는 이력으로만 남는다 |

## 5. 한계

- 내림 여부를 이력 문구로 판별하므로, 이력 문구 형식을 바꾸면 판별도 함께 바꿔야 한다(서버 `hidden_by_staff`와 화면 `hiddenByStaff`가 같은 접두를 쓴다). 열(`hidden_by_staff`)을 두는 방식은 스키마 변경이 필요해 하지 않았다.
- 목록에서 "내려진 민원"만 모아 보는 담당자 화면, 일괄 내리기, 자동 개인정보 탐지는 만들지 않았다.
- Swagger PDF(`docs/api/`)는 다시 만들지 않아 이 경로가 빠져 있다(실시간 `/docs`에는 있음).
- 이미 공개로 올라온 글을 알림 없이 내리므로, 작성자(게스트 포함)에게 내렸다는 안내는 가지 않는다.
