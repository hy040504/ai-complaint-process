# 사례 127: 공개 주소의 담당자 콘솔 API 화면 복구

- **사례 번호:** CASE-127
- **기록일:** 2026-11-23 KST
- **유형:** 버그·보안 경계
- **작업 상태:** 구현·검증 완료. 배포·공개 주소 확인은 아래 검증 참고
- **관련 문서:** [원격 서버 배포](../harness/원격_서버_배포.md) · [CASE-126](사례-126-Swagger-PDF-갱신과-오래된-점검-문제-정리-2026-11-23.md)

## 1. 증상

공개 주소의 담당자 사이트 `#/staff/api` 화면에서 Swagger가 나오지 않고 API 목록도 비어 있었다.

## 2. 원인

외부 공개 때(CASE-117 후속) 개발자 화면을 숨기려고 Cloudflare를 거친 요청(`CF-Ray` 헤더)의 `/docs`·`/swagger`·`/openapi*`·`/design/*`를 모두 404로 막았다. 그런데 담당자 콘솔의 API 화면은 바로 그 경로(`/swagger` iframe, `/openapi/openapi.json` 명세)를 불러 쓰므로 공개 주소에서는 항상 빈 화면이 됐다. 담당자 화면이 쓰는 경로까지 막은 설계 누락이다.

## 3. 조치

| 경로 | 공개 주소에서의 동작 |
| --- | --- |
| `/design/*` (디자인 목업) | 항상 404 (변경 없음) |
| `/docs`·`/swagger`·`/openapi*` | **담당자로 로그인한 경우에만** 열림. 비로그인·시민·위조 쿠키는 404 |
| 로컬·SSH 터널 접속 | 모두 열림 (변경 없음) |

- 판별은 요청의 `cj_staff` 쿠키를 서버 비밀키로 서명 검증해 `role=staff`와 사용자 번호가 있는지 보는 방식이다. 주소창으로 직접 연 문서에는 사이트 단서(헤더·Referer)가 없을 수 있어 쿠키를 직접 연다.
- 코드: `src/complaints/http.py`의 `hide_dev_pages_from_proxy()`·`_has_staff_session()`. 문서(README·배포 안내·그림)도 새 동작에 맞췄다.

## 4. 한계

- 로그인 담당자에게는 공개 주소에서 API 명세(전체 경로와 필드)가 보인다. 담당자 계정이 약하면(시연 계정) 명세가 노출될 수 있으니 시연 후 계정을 정리해야 한다.
- 세션 쿠키의 사용자가 이후 비활성화됐는지는 이 검사에서 다시 조회하지 않는다(쿠키 유효 기간 안에서만 열림). API 호출 자체는 기존대로 매번 사용자를 확인한다.
- Swagger의 "Try it out" 같은 API 호출은 기존 인증·권한 규칙을 그대로 따른다.
