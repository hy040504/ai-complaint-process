## 2. 점검에서 확인한 사항

기존 Python 17개 파일의 클래스·함수·메서드 정의 90개 중 64개에 docstring이 없었습니다. 수집 코드의 기존 구조는 Google 형식이었고 NumPy 형식 docstring은 없었습니다. 설명 주석에서 영문만으로 작성된 항목은 발견하지 못했습니다.

- `TableParser.__init__`, `clean_text`, `parse_rows`의 `preserve_lines` 설명이 누락되어 있었습니다.
- FAQ `parse_detail`은 실제로 안내 딕셔너리와 등록일의 튜플을 반환하지만 기존 설명은 딕셔너리만 안내했습니다.
- 일부 기존 단문 docstring은 인자·반환·예외·부작용을 설명하지 않았습니다.
- 재정렬을 꺼도 `max(limit, rerank_k)`건의 원문을 가져와 기본 5건 반환 시 컬렉션마다 20건을 조회했습니다.
- `search`의 `defaultdict`, `ingest`·`verify`의 `Counter` import는 사용하지 않았습니다.

## 4. 검증 결과와 한계

- docstring 보완 직후 기존 Python 17개의 AST에서 docstring을 제외한 실행 구조가 원본과 같음을 확인했습니다. 이후 실행 변경은 후보 조회 범위와 미사용 import 정리에 한정합니다.
- Docker Python 3.12에서 `RUN_PG_TESTS=1`로 `rag/tests`를 실행해 **25개가 통과**했습니다. 새 12개는 모델·DB 대역으로 결과 순위·컬렉션 분리·후보 조회 수·`requires_gate` 계약을 확인합니다.
- 최종 Python 18개의 정의 93개에 한국어 docstring을 확인했고, 인자 설명 누락·영문만 있는 설명 주석·미사용 import는 정적 검사에서 발견되지 않았습니다. 전체 검사 대상 설명 주석은 Python·SQL·설정 파일을 합쳐 20개였습니다.
- API 재시작 후 같은 질문의 재정렬 제외 검색을 비교했습니다. FAQ·사례 각각 5개 결과를 반환했고 시간 필드를 제외한 전체 응답이 수정 전과 일치했습니다.
- 실제 재정렬 사용 경로도 `FAQ_대형폐기물` 한 예제로 확인했습니다. 재정렬 후보 20개와 검색 전용 계약을 유지했고 기대 문서 `1314210`이 1위였습니다.
- Markdown 26개와 상대 링크·이미지 경로 311개를 검사해 누락 경로·앵커 오류가 없음을 확인했습니다. 사례 번호 6개도 중복 없이 연결됩니다.

실행 요약과 원본 해시는 [코드 점검 보고서](../../rag/reports/코드_점검_2026-10-25.json)에 보관합니다. 주석의 의미는 코드와 수동 대조했으며 정적 검사만으로 모든 설명의 정확성을 보장하지는 않습니다. 기존 10문항 모델 평가 전체를 다시 수행한 결과가 아니고, 전체 검색 지연의 개선율도 측정하지 않았습니다.

## 5. 적용·복구와 후속 작업

이 사례를 포함하는 코드 커밋과 원격 `main`을 대조해 GitHub 반영 여부를 확인합니다. 실행 중인 검색 API는 소스 마운트 방식이므로 재시작 후 새 코드를 사용하며, 다른 서비스·GPU 작업은 적용 대상이 아닙니다.

문제 발생 시 후보 조회 범위 변경을 되돌리고 검색 API를 재시작합니다. 데이터·색인 변경이 없어 복구를 위한 재적재는 필요하지 않습니다. 실제 민원 자동 응답 품질·LLM 선정·부서 업무와 FAQ 현행성 검증은 별도 후속 과제입니다.
