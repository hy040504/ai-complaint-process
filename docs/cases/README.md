## 어떤 작업을 사례로 남기는가

- 재현 가능한 버그, 장애, 검색·판정 실패를 발견하거나 수정한 경우.
- 데이터 필드·부서 매핑·검색·응답 정책·실행 방식이 의미 있게 바뀐 경우.
- LLM·Jev·학습·관할처럼 이후 구현에 영향을 주는 결정을 한 경우.
- 검증을 통해 기존 가정을 바꾸거나 미해결 위험을 확인한 경우.

단순 오탈자·링크 수정은 관련 사례에 보충할 수 있습니다. 같은 원인과 해결 범위의 기록이 있으면 그 사례를 갱신하고, 다른 원인의 재발이면 새 번호를 만들고 이전 사례를 연결합니다.

## 번호·파일명·상태

- 식별자는 `CASE-001`부터 증가시킵니다. 파일명은 `사례-001-한국어-주제-YYYY-MM-DD.md` 형식이며 날짜는 UTC 기준입니다. 영문 모델명·기술명은 함께 쓸 수 있습니다.
- 새 번호는 현재 최대 번호 다음을 사용하고, 이미 배정한 번호는 재사용하거나 재정렬하지 않습니다. 병렬 브랜치를 합칠 때 번호 충돌을 확인합니다.
- 파일명의 날짜는 해당 작업·사건의 기준일입니다. 뒤늦게 기록할 때는 본문에 실제 기록일을 별도로 적습니다. 이후 갱신 때문에 파일명을 바꾸지 않습니다.
- 작업 상태는 `확인 필요 → 분석 중 → 작업 중 → 검증 대기 → 완료`를 기본으로 하고, 필요하면 `보류`, `대체됨`을 사용합니다. 재발하면 다시 열고 재현 일자를 추가합니다.
- 완료에는 유형별 근거가 필요합니다. 버그는 수정과 필요한 검증, 설계는 결정 내용과 문서 반영을 기록합니다. 설계 완료로 기능 구현·배포 완료를 표시하지 않습니다.
- 코드·DB·문서 적용 범위와 로컬 검증·원격 업로드·운영 반영 여부는 따로 적습니다. 코드 커밋과 문서 커밋이 다르면 각각 구분합니다.

## 작성·갱신 순서

1. 이 색인에서 같은 문제와 관련 사례를 찾고, 새 사례가 필요하면 [양식](사례_작성_양식.md)을 복사합니다.
2. 관찰한 사실, 기대 동작, 재현 조건, 영향 범위를 먼저 적습니다. 원인 가설은 확인된 원인과 구별합니다.
3. 변경 파일·계약과 실제 조치를 기록합니다. 데이터·모델·정책 변경은 출처 ID, 해시, 리비전 등 필요한 재현 정보를 남깁니다.
4. 수행한 검증만 일자·환경·결과·증거 경로와 함께 적고, 미실행·실패·미검증 항목을 남깁니다. 개인정보·쿠키·자격 증명은 기록에서 제거합니다.
5. 사례 본문과 이 색인의 상태를 맞추고, 관련 기준 문서와 [CHANGELOG](../../CHANGELOG.md)를 연결합니다. 남은 구현은 [실행 계획](../../plan/harness-roadmap.md)에 반영합니다.

과거 수치와 검증 결과는 당시의 기록으로 보존합니다. 후속 결과는 날짜를 붙여 추가하고, 최신 동작을 설명하는 기준 문서는 함께 갱신합니다. 실행하지 않은 테스트나 업로드를 완료했다고 적지 않습니다.
