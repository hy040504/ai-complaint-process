## 2. 배경·증상과 기대 동작

- 관찰한 사실과 영향: 2026-10-30 설계(`02_complaint_app.sql`)는 정규화 7테이블인데, 실행 구조는 `complaints`(jsonb) 1테이블과 `idempotency`다. 설계 문서를 보면 실제 구조를 알 수 없었다. 시연 데이터의 시연 표시(`is_synthetic`)도 없었다.
- 기대 동작 또는 요구사항: 사용자 결정에 따라 현재 구조를 유지하고, 설계 문서를 현재 구조에 맞춘다. 목록·필터에 쓰는 값은 DB가 검사하고, 시연 민원은 표시되어야 한다.
- 확인 근거와 시점: 2026-11-06 DB의 테이블·payload 키 조회, `docs/harness/업무DB_실행설계.md` 대조.

## 3. 재현·확인 방법

- 재현 환경·선행 조건: 로컬 PostgreSQL에 `complaint_app` 스키마가 있고 서버가 한 번 기동된 상태.
- 확인 단계와 결과: `\dt complaint_app.*`으로 2개 테이블만 확인. `payload` 키는 camelCase(`isSynthetic` 포함 키 없음). 설계 SQL의 7테이블과 대조해 불일치를 확인했다.
- 설계 대비 판단 근거: 실행 설계 README(2026-10-30 설계 복사본)가 "2026-11-05 이후 실행용 파일은 `src/complaints/schema/complaint_app.sql`"이라고 적고 있어, 실행 구조를 바꾸지 않고 설계 쪽을 맞추는 방향을 택했다.

## 4. 원인 분석 또는 결정 근거

- 확인된 원인: CASE-031에서 저장을 jsonb로 통일하면서 설계 문서를 갱신하지 않았다. 설계 폴더의 기준일 표기도 없었다.
- 검토한 선택지와 결정 이유:
  1. 현 구조 유지, 설계 문서를 실제 구조에 맞춤 (채택). 서비스·API를 다시 짜지 않고, 검색용 칼럼만 생성 칼럼으로 추가할 수 있다.
  2. 7테이블 이관 (미채택). 저장소·서비스·테스트를 모두 다시 작성해야 하고, 시연 기한 안에서 얻는 이득이 작다.
- 아직 확인하지 않은 가설: 목록 쿼리를 생성 칼럼으로 바꾸면 응답이 빨라지는지는 측정하지 않았다.

## 7. 완료 조건·후속 작업·복구

- 완료로 판단한 조건과 충족 근거: 설계 문서가 실제 구조를 설명하고, 실행 SQL·모델·DB 상태가 같은 구조이며, 자동 테스트와 실제 DB 확인이 통과했다. 충족.
- 남은 작업: 목록 쿼리를 페이지네이션·생성 칼럼 기반으로 바꾸기, `ui04` 목업을 현재 구조에 맞춰 연결하기, 설계 PDF·PPTX 재작성 여부 결정, 7테이블 이관 재검토 여부 결정.
