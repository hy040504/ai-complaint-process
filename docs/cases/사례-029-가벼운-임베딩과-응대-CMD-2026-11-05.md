## 2. 배경·증상과 기대 동작

- 관찰한 사실과 영향: `BAAI/bge-m3`는 1024차원·약 2GB라 CPU 일반 PC에서 부담이 크다. 응대는 `python -m rag assist`가 있으나 Windows 더블클릭 경로가 없었다.
- 기대 동작 또는 요구사항: 아무 컴퓨터나 돌릴 가벼운 임베딩을 기본으로 잡고, CMD로 민원 문장을 넣으면 검색+LLM 응대를 본다.
- 확인 근거와 시점: 2026-11-05 사용자 요청.

## 3. 재현·확인 방법

- 비교한 기존 동작: 고정 BGE-M3 1024차원, CLI만 있는 응대.
- 판단 근거: 한국어를 포함한 다국어 검색용 `intfloat/multilingual-e5-small`(약 117M, 384차원, 최대 512토큰)을 기본으로 한다. 기존 색인은 `RAG_EMBEDDING_PROFILE=bge-m3`로 유지한다.

## 4. 원인 분석 또는 결정 근거

- 확인된 원인·근거: 질의 임베딩과 색인 임베딩은 같은 모델이어야 하므로, 가벼운 실행을 원하면 색인도 다시 만들어야 한다.
- 검토한 선택지와 결정 이유: MiniLM 128토큰은 FAQ 조건 본문에 짧다. e5-small은 512토큰·질문/문서 접두가 있고 CPU에서 부담이 적다. 재정렬 모델은 그대로 두되 API 시작 때 미리 올리지 않는다. CMD 기본은 재정렬 끔.

- 5,109건 재임베딩과 실제 PostgreSQL 검색 회귀, Luna 실측, `ask-assist.cmd` 실검색은 이 변경에서 실행하지 않았다.
- 기존 `complaint_rag.dump`(1024차원)는 `RAG_EMBEDDING_PROFILE=bge-m3`로 복원한다.
- e5-small은 512토큰을 넘는 본문을 벡터에서만 자른다. FAQ 원문 저장과 BM25 토큰은 유지한다.

## 7. 완료 조건·후속 작업·복구

- 완료: 기본 임베딩이 CPU용 e5-small이고, CMD가 검색 API 위에서 응대를 보여 준다.
- 남은 작업: 운영 DB에서 `--reembed` 후 검색 예제 10건 재평가.
- 되돌림: `RAG_EMBEDDING_PROFILE=bge-m3` 또는 이전 config 상수. 이미 384로 맞춘 열은 다시 1024 재임베딩이 필요하다.
