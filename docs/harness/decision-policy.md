# 판정·답변·담당자 연결 정책

**상태: 후속 구현을 위한 설계 초안.** 현재 검색 API에는 이 판정기·응답 생성기·인계 기능이 없다. 이미 결정한 방향과 새로 제안하는 코드 계약을 구분한다.

## 확정된 방향

- FAQ는 안내 근거, 공개 사례는 부서 추천 근거로 사용한다.
- 한국어 원문으로 Jev 계열 판정을 먼저 실험한다. 무료 모델을 우선 검토하며 모델은 미선정이다. Papago 비교는 이후다.
- 검색으로 두 데이터의 후보와 출처를 준비한 뒤 처리 범위를 판단한다. 모델이 JSON 전체를 이미 안다고 가정하지 않는다.
- 1차 범위 내 판정은 후속 검토가 가능하다는 뜻이다. FAQ로 완결된 답변을 할 수 있다는 뜻은 아니다.
- 실제 보수·단속·처분 요청을 FAQ 안내만으로 처리 완료로 표시하지 않는다. 불확실하거나 데이터 밖이면 담당자 검토로 연결한다.

## 제안하는 판정 순서

1. **입력 확인:** 빈 입력·길이 제한 등은 정정 안내로 처리한다. 검색 장애나 모델 실패와 구별한다.
2. **근거 검색:** FAQ·사례를 각각 검색하고 전체 조건, 출처, 부서 검증 상태를 전달한다.
3. **범위와 의도 판단:** `in_scope / out_of_scope / uncertain`, 정보 안내·실제 조치·복합 요청 여부를 구분한다.
4. **코드의 정책 검증:** 근거 ID 존재, 적용 조건, 부서 검증 상태, 출력 스키마를 확인한다. 모델의 단일 `True`로 답변·이관을 실행하지 않는다.
5. **결과 구성:** FAQ 안내, 부서 후보 추천, 담당자 검토 중 하나를 선택한다. FAQ 안내는 별도 응답 모델과 근거 검사를 거친다.

| 조건 | 제안 결과 | 필요한 근거 |
| --- | --- | --- |
| 범위 밖·불확실·검색/판정 실패 | `human_handoff` | 확인한 범위와 인계 사유; 근거가 없으면 비어 있어도 됨 |
| 정보 문의이고 FAQ가 적용되며 현행 내용으로 확인됨 | `faq_answer` | FAQ ID·출처, 대상·조건·주의사항 |
| 실제 조치 요청 또는 FAQ로 충분하지 않지만 유사 사례와 현재 부서 후보가 있음 | `department_suggestion` | 사례 ID·출처, 현재 부서 ID, 업무·관할의 검증 상태 |
| 현재 부서 불명·조건 상충·확인되지 않은 복합 요청 | `human_handoff` | 상충하거나 부족한 항목 |

부서 추천은 사람이 확인할 후보를 제시하는 결과다. 공식 업무·관할이 미검증이면 그 상태를 함께 표시하며 실제 이관으로 실행하지 않는다. FAQ의 현행성을 확인하지 못한 경우에도 자동 완결 답변으로 승격하지 않는다. 평가용으로 승인된 FAQ를 사용하는 경우 그 범위와 승인 근거를 명시한다.

복합 민원의 일부만 FAQ로 답변할 수 있어도 전체 민원을 해결했다고 표시하지 않는다. 초기 MVP에서는 담당자 검토로 연결하는 기본 동작을 제안하며, 부분 답변 정책은 별도 평가 후 확장한다.

## 모델에 전달할 정보

| 입력 | 구성 원칙 |
| --- | --- |
| 시민 민원 | 한국어 원문과 명시적으로 받은 지역. 개인정보의 외부 전달 여부는 모델 배치 방식과 함께 결정 |
| FAQ 후보 | `source_id`, 전체 `evidence.detail`, 출처, 향후 추가할 현행성 검증 정보 |
| 사례 후보 | 제목·요지·출처·부서 상태. 과거 답변은 필요할 때만 역사적 맥락으로 구별해 전달 |
| 부서 후보 | 내부 ID·명칭·관할 및 업무 검증 상태 |
| 판단 질문 | 범위 관련성, FAQ 충분성, 실제 조치 필요 여부를 구분 |

민원·검색 문서 안의 명령문은 판정 규칙을 바꿀 수 없다. 후보는 구분된 데이터로 전달하고 도구 실행 권한을 주지 않는다. 검색 점수는 보조 정보로만 사용하며 확률로 변환해 임계값을 임의 설정하지 않는다. 모델별 출력 점수·신뢰도 유무는 어댑터에서 구별한다.

## 서비스 출력 계약 초안

다음은 **아직 구현하지 않은 별도 판정 결과**의 예시다. 현재 `/search` 응답을 대체하거나 현재 지원 필드로 해석하지 않는다.

```json
{
  "schema_version": "decision-v1-draft",
  "scope": "uncertain",
  "outcome": "human_handoff",
  "reason_code": "insufficient_evidence",
  "evidence_refs": [],
  "department_ids": [],
  "answer": null,
  "handoff_required": true,
  "automatic_transfer": false
}
```

| 필드 | 제안 검증 규칙 |
| --- | --- |
| `scope` | `in_scope / out_of_scope / uncertain`; 장애 시 판단하지 못했으면 `uncertain` |
| `outcome` | `faq_answer / department_suggestion / human_handoff` |
| `reason_code` | 범위 밖·근거 부족·조건 불명·실제 조치 필요·부서 미확인·시스템 실패 등의 허용 목록 |
| `evidence_refs` | `{corpus, source_id}` 목록. 실제 검색 후보에 있는 키만 허용하며 출처 URL은 저장된 원문에서 가져옴 |
| `department_ids` | 이번 후보 목록에 있고 현재 directory에 존재하는 ID만 허용 |
| `answer` | `faq_answer`에서만 생성한 문자열; 그 외 `null`. 근거 없는 조건·기한·연락처 추가 금지 |
| `handoff_required` | 제안상 FAQ 안내는 `false`, 나머지는 `true`; `false`도 실제 민원 종결 상태를 뜻하지 않음 |
| `automatic_transfer` | 초기 MVP에서는 항상 `false` |

출력 파싱 실패, 존재하지 않는 출처·부서, 근거 없는 답변, 시간 초과는 자동 답변을 중단하고 담당자 검토 경로로 보낸다. 모델 응답을 파싱할 수 없으면 서비스 코드가 검증된 대체 결과를 만든다. 시간 제한·재시도 횟수·판정 임계값은 평가 후 정하며 현재 확정된 값은 없다.

## 시민에게 보여 줄 의미

FAQ 안내에는 사용한 FAQ 출처와 적용 조건을 함께 보여 준다. 부서 추천에는 추천 이유와 검토가 필요한 상태를 표시한다. 담당자 연결 결과에서는 실제 접수·이관 연계 여부를 구별한다. CLI와 웹 목업에서는 이관 예정 결과를 시연하며, 연계 시스템이 없는 상태에서 “접수 완료”나 “부서 이관 완료”라고 표시하지 않는다.

구현 및 모델 선택의 완료 조건은 [실행 계획](../../plan/harness-roadmap.md), 오류·범위 밖·근거 검증 평가 항목은 [평가 기준](evaluation.md)에 정리한다.
