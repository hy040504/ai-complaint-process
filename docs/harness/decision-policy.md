# 판정·답변·담당자 연결 정책

**상태: 설계 초안 + 로컬 응대 계층 일부 구현, 2026-11-05 갱신.** 검색 API는 여전히 `retrieval_only` / `requires_gate`만 반환한다. 판정·정책 검사·조건부 FAQ 생성은 `src/assist`와 `POST /api/v1/assist`·`/assist/stream`에 있다. 최종 모델·현행성 허용 목록·평가 임계값은 미정이다. 사용자 결정은 **LLM + RAG 우선, Jev 추후 추가**다.

## 확정된 방향

- FAQ는 안내 근거, 공개 사례는 부서 추천 근거로 사용한다.
- 초기 MVP에서는 범용 LLM으로 판정과 FAQ 답변을 수행한다. Jev는 기본 성능을 확보한 뒤 추가한다.
- 한국어 원문과 무료 모델 우선을 유지하며 최종 LLM은 미선정이다. Papago 비교는 이후다.
- 검색으로 두 데이터의 후보와 출처를 준비한 뒤 처리 범위를 판단한다. 모델이 JSON 전체를 이미 안다고 가정하지 않는다.
- 1차 범위 내 판정은 후속 검토가 가능하다는 뜻이다. FAQ로 완결된 답변을 할 수 있다는 뜻은 아니다.
- 실제 보수·단속·처분 요청을 FAQ 안내만으로 처리 완료로 표시하지 않는다. 불확실하거나 데이터 밖이면 담당자 검토로 연결한다.

## 제안하는 판정 순서

1. **입력 확인:** 빈 입력·길이 제한 등은 정정 안내로 처리한다. 검색 장애나 모델 실패와 구별한다.
2. **근거 검색:** FAQ·사례를 각각 검색하고 전체 조건, 출처, 부서 검증 상태를 전달한다.
3. **LLM 판정 호출:** `in_scope / out_of_scope / uncertain`, 정보 안내·실제 조치·복합 요청을 구분하고 처리 경로·근거 ID를 구조화해 제안한다. 이 호출에서는 시민용 답변을 만들지 않는다.
4. **코드의 정책 검증:** 실제 검색 근거 ID, 적용 조건·현행성 기록, 부서 검증 상태, 출력 스키마를 확인한다. 모델의 단일 `True`나 자기 보고 confidence로 답변·이관을 실행하지 않는다.
5. **조건부 답변 호출:** `faq_answer`가 허용된 경우 같은 범용 LLM을 다시 호출해 선택된 FAQ 전체로 답변을 작성한다. 부서 추천·담당자 검토 문구는 템플릿으로 구성한다.
6. **결과 검사:** 답변의 출처·필수 조건·수치 등을 확인하고 실패하면 담당자 검토로 전환한다. 같은 모델의 자기 검토 결과만으로 정확성을 보장하지 않는다.

두 LLM 호출은 같은 모델 가중치를 재사용하는 제안이다. 별도 판정 모델·Jev는 초기 필수 요소가 아니다. 검색의 `requires_gate`는 이러한 후속 판단 필요를 뜻하며 검색 API 계약은 유지한다.

| 조건 | 제안 결과 | 필요한 근거 |
| --- | --- | --- |
| 범위 밖·불확실·검색/판정 실패 | `human_handoff` | 확인한 범위와 인계 사유; 근거가 없으면 비어 있어도 됨 |
| 정보 문의이고 FAQ가 적용되며 현행 내용으로 확인됨 | `faq_answer` | FAQ ID·출처, 대상·조건·주의사항 |
| 실제 조치 요청 또는 FAQ로 충분하지 않지만 유사 사례와 현재 부서 후보가 있음 | `department_suggestion` | 사례 ID·출처, 현재 부서 ID, 업무·관할의 검증 상태 |
| 현재 부서 불명·조건 상충·확인되지 않은 복합 요청 | `human_handoff` | 상충하거나 부족한 항목 |

부서 추천은 사람이 확인할 후보를 제시하는 결과다. 공식 업무·관할이 미검증이면 그 상태를 함께 표시하며 실제 이관으로 실행하지 않는다. FAQ의 현행성을 확인하지 못한 경우에도 자동 완결 답변으로 승격하지 않는다. 초기에는 사람이 확인한 FAQ의 허용 목록에 원문 해시·확인 일자·근거를 기록하는 안을 제안하며, 이 기록은 아직 구현되지 않았다. `retrieved_at`을 현행성 확인으로 대신하지 않는다.

복합 민원의 일부만 FAQ로 답변할 수 있어도 전체 민원을 해결했다고 표시하지 않는다. 초기 MVP에서는 담당자 검토로 연결하는 기본 동작을 제안하며, 부분 답변 정책은 별도 평가 후 확장한다.

## 모델에 전달할 정보

| 입력 | 구성 원칙 |
| --- | --- |
| 시민 민원 | 한국어 원문과 명시적으로 받은 지역. 개인정보의 외부 전달 여부는 모델 배치 방식과 함께 결정 |
| FAQ 후보 | `source_id`, 전체 `evidence.detail`, 출처, 향후 추가할 현행성 검증 정보 |
| 사례 후보 | 제목·요지·출처·부서 상태. 과거 답변은 필요할 때만 역사적 맥락으로 구별해 전달 |
| 부서 후보 | 내부 ID·명칭·관할 및 업무 검증 상태 |
| 판단 질문 | 범위 관련성, FAQ 충분성, 실제 조치 필요 여부를 구분 |

민원·검색 문서 안의 명령문은 판정 규칙을 바꿀 수 없다. 후보는 구분된 데이터로 전달하고 도구 실행 권한을 주지 않는다. 검색 점수는 보조 정보로만 사용하며 확률로 변환해 임계값을 임의 설정하지 않는다. LLM이 생성한 confidence도 정답 확률로 해석하지 않는다. FAQ 답변 호출에는 선택한 FAQ와 적용 조건을 전달하고 사례의 과거 답변을 현재 정책 근거로 섞지 않는다.

JSON Schema 제한·파싱·ID 대조는 형식과 참조 무결성 검사다. 조건의 의미적 적용 여부와 답변의 사실성은 이것만으로 보장되지 않으므로, 검수된 자료·한국어 평가·불확실 시 보류를 함께 적용한다.

## 서비스 출력 계약 초안

다음은 **아직 구현하지 않은 별도 판정 결과**의 예시다. 현재 `/search` 응답을 대체하거나 현재 지원 필드로 해석하지 않는다.

```json
{
  "schema_version": "decision-v1-draft",
  "scope": "uncertain",
  "intent": "unclear",
  "outcome": "human_handoff",
  "reason_code": "insufficient_evidence",
  "evidence_refs": [],
  "department_ids": [],
  "answer": null,
  "handoff_required": true,
  "automatic_transfer": false
}
```

| 필드 | 제안 검증 규칙 |
| --- | --- |
| `scope` | `in_scope / out_of_scope / uncertain`; 장애 시 판단하지 못했으면 `uncertain` |
| `intent` | `information / action / mixed / unclear`; FAQ 안내는 `information`일 때만 허용하는 초기 정책 |
| `outcome` | `faq_answer / department_suggestion / human_handoff` |
| `reason_code` | 범위 밖·근거 부족·조건 불명·실제 조치 필요·부서 미확인·시스템 실패 등의 허용 목록 |
| `evidence_refs` | `{corpus, source_id}` 목록. 실제 검색 후보에 있는 키만 허용하며 출처 URL은 저장된 원문에서 가져옴 |
| `department_ids` | 이번 유효 후보 목록에 있고 현재 directory에 존재하는 ID만 허용; 미확인·검토 대상 사례로 확정하지 않음 |
| `answer` | `faq_answer`에서만 생성한 문자열; 그 외 `null`. 근거 없는 조건·기한·연락처 추가 금지 |
| `handoff_required` | 제안상 FAQ 안내는 `false`, 나머지는 `true`; `false`도 실제 민원 종결 상태를 뜻하지 않음 |
| `automatic_transfer` | 초기 MVP에서는 항상 `false` |

이 예시는 응대 계층이 최종 조합할 결과다. 첫 판정 호출에서는 `answer=null`이며 정책 검사를 통과한 FAQ 경로에서만 답변을 채운다. `faq_answer`는 `scope=in_scope`, `intent=information`, 유효 FAQ 근거와 확인된 적용 조건을 요구한다. 다른 경로로 전환하면 생성된 답변을 노출하지 않는다.

출력 파싱 실패, 존재하지 않는 출처·부서, 근거 없는 답변, 시간 초과는 자동 답변을 중단하고 담당자 검토 경로로 보낸다. 모델 응답을 파싱할 수 없으면 서비스 코드가 검증된 대체 결과를 만든다. 시간 제한·재시도 횟수는 평가 후 정한다. 초기부터 confidence 임계값을 임의로 추가하지 않는다.

## Jev 후속 확장

LLM + RAG의 판정·답변 기준 성능을 먼저 확보한다. 이후 같은 근거와 출력 계약으로 Jev 판정 대체 또는 불확실 사례의 추가 검토를 비교한다. 정책 검사와 FAQ 생성은 재사용하며 Jev를 끈 기본 경로도 유지한다. 제안 후보와 비교 방법은 [모델·미세조정 제안](../../plan/모델_선정과_미세조정_제안.md)을 참고한다.

## 시민에게 보여 줄 의미

FAQ 안내에는 사용한 FAQ 출처와 적용 조건을 함께 보여 준다. 부서 추천에는 추천 이유와 검토가 필요한 상태를 표시한다. CLI의 검토 안내와 웹 서버에 실제 저장된 검토 요청도 구별한다.

시연 웹은 민원 등록·답변 교환 서버까지 구현할 계획이다. 서버 저장이 성공한 경우 **시연 서비스 내 등록 완료**를 표시할 수 있으며, `human_handoff`는 해당 민원을 검토 목록에 연결하는 방식으로 제안한다. 담당자 답변과 시민 추가 문의는 실제 저장 결과로 보여 준다. AI가 실패해도 등록된 글을 보존하고 실패·검토 상태를 표시한다.

이 내부 등록·검토 연결은 자동 부서 이관과 구별하며 `automatic_transfer=false`를 유지한다. 청주시 공식 접수번호·기관 배정·외부 부서 이관 완료는 해당 연계가 구현·확인된 경우에만 표시한다. 상세 범위는 [시연 웹·민원 서버 계획](../../plan/시연_웹_게시판과_민원_서버_구현계획.md)을 따른다.

구현 및 모델 선택의 완료 조건은 [실행 계획](../../plan/harness-roadmap.md), 오류·범위 밖·근거 검증 평가 항목은 [평가 기준](evaluation.md)에 정리한다.

## 답변 편집·게시와 실시간 상태: 2026-10-27 제안

[통합 상세설계](../../plan/민원_웹_MVP_상세설계와_분야별_작업계획.md)는 AI 작성 표시·담당자 수정·작업 모니터 요구를 구체화한다. 판정 결과와 답변 게시 여부는 다른 계약이다. 개발 초기에는 검토 우선 모드로 검사하고, 검수 FAQ 허용 목록·코드 검사를 통과한 `faq_answer`에만 제한 자동 안내를 비교하는 안이다. 자동 게시 활성화 범위는 아직 확정하지 않았다.

AI 원본을 보존한 새 수정 버전을 저장하고, 사람이 편집한 답변은 기원 표시를 유지한 담당자 게시로 기록한다. 수정본에 과거 자동 검사 통과를 그대로 적용하지 않는다. 미게시 초안은 시민에게 제공하지 않으며, 담당자 모니터에는 실제 작업 단계·시간·검사 상태만 전달한다. AI의 내부 추론을 표시하지 않는다. 늦은 AI 결과·재생성이 담당자의 편집본·게시본을 덮어쓰지 않게 버전을 확인한다.
