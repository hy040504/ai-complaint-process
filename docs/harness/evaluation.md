# 검증과 평가 하네스

검색 순위가 맞는지, 데이터가 보존되는지, 자동으로 응답해도 되는지는 서로 다른 평가다. 현재 도구가 검증하는 범위와 후속 판정 평가를 분리한다. 2026-10-25 변경 방향에 따라 **Jev 없는 LLM + RAG를 먼저 평가**하고, Jev 추가와 LoRA는 이후 별도 실험으로 비교한다.

## 현재 실행 가능한 검증

모든 명령은 저장소 루트 기준이다. 현재 네이티브 환경의 실행 방법은 [네이티브 운영 안내](네이티브_운영.md)를 따른다.

| 검증 | 확인하는 것 | 확인하지 않는 것 |
| --- | --- | --- |
| `rag/tests` | 원본 보존, 조건 유지, 부서 분리, RRF, Kiwi, 실제 SQL·필터·롤백, 재정렬 사용 여부에 따른 후보 조회와 순위 | 모델의 한국어 판정 정확도 |
| `rag.verify` | JSON과 DB의 키·payload·본문·벡터 형태, BM25 길이/빈도 통계 일관성, 부서 ID·별칭, HNSW 존재 | 임베딩의 의미 품질, FAQ 현행 정책, 업무 관할 정답 |
| `rag.evaluate` | API 예제에서 기대 문서/부서가 상위 5개 안에 있는지, 검색 전용 계약 | 자동 답변 정확도, 범위 밖 탐지율, 운영 임계값 |

```bash
source scripts/네이티브_환경.sh
RUN_PG_TESTS=1 .venv/bin/python -m pytest rag/tests -q -p no:cacheprovider
.venv/bin/python -m rag.verify
python3 -m rag.evaluate --output .rag-cache/reports/retrieval-current.json
```

`scripts/검색DB_준비.sh`로 준비한 테스트 템플릿과 DB 생성 권한을 사용한다. `RUN_PG_TESTS=1`을 빼면 격리 DB 테스트 3개를 건너뛴다. 템플릿에는 확장만 포함하며 운영 데이터는 복사하지 않는다. API 포트를 바꿨으면 평가 명령에도 `--api-url`을 지정한다.

수동 검색 확인은 [검색 테스트 메뉴](../../rag/README.md#검색-테스트-메뉴)를 사용할 수 있다. 2026-10-28에는 네이티브 환경에서 화면 회귀 2개를 포함한 전체 테스트 27개가 통과했다. [CASE-011](../cases/사례-011-검색-테스트-터미널-메뉴-추가-2026-10-28.md)

## 변경별 필요한 확인

| 변경 | 최소 확인 |
| --- | --- |
| 문서·README | 상대 링크, 코드 경로, 명령 옵션, 구현/제안 구분, diff 확인 |
| 수집·정규화·본문 구성 | 관련 테스트, 원본 변경·삭제 검토, 재적재 후 `rag.verify` |
| SQL·RRF·토큰화·지역 필터 | 코드·격리 DB 테스트, 색인 호환성, 관련 검색 회귀 |
| 임베딩·재정렬 모델 | 모델 리비전·색인 호환성, 검색 회귀, 같은 입력의 품질·시간 비교 |
| API 입력·출력 | 정상 입력, `400/422/503` 경로, 검색 전용 계약, CLI 호환성 |
| LLM 판정·FAQ 응답 연결 | 아래 판정·답변 평가, 출처·조건 검사, 장애 대체 경로; 초안 평가셋은 `scripts/응대_평가.py`(기본 개발셋) |
| 시연 웹·민원 업무 서버 | 등록·영속화·조회·답변 교환·역할·상태 전이·중복 제출·AI 실패 시 민원 보존; 현재 미구현 |
| 후속 Jev·LoRA 도입 | 같은 검색 근거·보류 평가셋으로 기본 LLM + RAG와 각각 비교 |

검증은 변경 영향에 맞게 선택한다. 문서 변경 때문에 전체 벡터 재생성이나 긴 모델 평가를 실행하지 않는다. 의미가 달라진 코드에는 그 동작을 확인하는 테스트를 추가하되 구현을 그대로 복사한 테스트로 대체하지 않는다.

## 추가할 웹·민원 서버 검증

아래는 시연 웹과 업무 서버를 구현할 때 필요한 인수 확인이며 현재 25개 코드·DB 테스트에 이미 포함된 결과가 아니다. 상세 범위는 [웹·민원 서버 계획](../../plan/시연_웹_게시판과_민원_서버_구현계획.md)을 따른다.

- 등록한 글이 목록·상세에 보이고 새로고침·서버 재시작 후에도 남는지 확인한다.
- 담당자 답변과 시민 추가 문의가 같은 민원에 저장되고 역할별 화면에 일관되게 나타나는지 확인한다.
- 공개 범위·작성자·담당자 역할에 맞지 않는 조회·답변·상태 변경을 서버에서 거부하는지 확인한다.
- 저장 실패에는 등록 완료를 표시하지 않고, 저장 후 AI가 실패해도 글이 남아 담당자 검토로 이어지는지 확인한다.
- 중복 제출·응답 재시도·늦게 끝난 AI 검토가 중복 글·답변이나 다른 입력 버전의 결과를 만들지 않는지 확인한다.
- 시연 등록 상태와 공식 행정 접수·이관 상태, 민원 업무 데이터와 RAG 지식 데이터가 구별되는지 확인한다.

웹 전체 지연은 등록 저장·검색·판정·답변 생성·조회 시간을 나눠 측정한다. 게시판 동작 검증과 AI 응답 정확도 평가는 각각 기록한다.

2026-10-27 추가 요구의 구체적 인수 시나리오는 [통합 상세설계 20절](../../plan/민원_웹_MVP_상세설계와_분야별_작업계획.md#20-인수-시나리오와-통과-조건)의 T01~T16을 따른다. CRUD·복구, AI 기원과 수정 이력, 초안 비노출, 동시 게시 충돌, SSE 재연결·중복·권한 회수, 작업자 중단·늦은 결과 차단을 포함한다. 실시간 화면은 실제 단계 이벤트로 검증하고 꾸며낸 진행률·타이핑으로 통과 처리하지 않는다. 이 항목들은 아직 구현·실행하지 않았다.

## 기존 결과의 해석

2026-10-25 코드·주석 점검에서 기존 13개와 후보 조회 회귀 12개, 총 **25개 테스트가 통과**했다. 추가 회귀는 모델·DB 대역을 사용하며 실제 모델의 검색 품질 평가와 구별한다. 변경·실행 근거는 [CASE-006](../cases/사례-006-한국어-주석과-커밋-규칙-정비와-검색-조회-최적화-2026-10-25.md)에 있다.

2026-11-06 e5-small-ko 색인에서 `python -m rag.evaluate --output rag/reports/retrieval-e5-small-ko.json` 10건이 통과했다. FAQ 5개·부서 4개는 기대 문서/부서가 1위였고, 범위 밖 1개는 `retrieval_only`·`requires_gate`만 확인한다. 자동 답변 정확도 측정이 아니다. [검색 보고서](../../rag/reports/retrieval-e5-small-ko.json)

2026-11-06 `scripts/응대_평가.py`는 초안 응대 평가셋의 **갈래**만 본다. 문항은 유형별 29건(개발 26·보류 3)이다. 기본 실행은 개발셋이며 보류 문항은 프롬프트 조정에 쓰지 않는다. `FAQ_성인여권`과 `FAQ_생활쓰레기시간`은 검색 Hit가 있어도 FAQ 본문에 질문 항목이 없어 `human_handoff`/`condition_unclear`가 맞다. 조건 부족 사유는 코드가 `faq_answer`를 막는다. 개발셋 26/26은 운영 모델 선정이 아니다. 400문항은 제안이다. [초안 응대 보고서](../../rag/reports/assist-eval-draft.json) · [문항](../../rag/assist_eval_queries.json) · [CASE-064](../cases/사례-064-초안응대평가셋확대-2026-11-06.md)

PREFIX 조립 적격은 `src.assist.prefix_cache.prefix_cache_report`가 확인한다. openai_api `cached_tokens`는 `.env`의 키가 비어 건너뛰었다. [조립 보고서](../../rag/reports/prefix-cache-assembly.json) · [비교](../../rag/reports/assist-provider-compare.json)

2026-10-24 기준 코드·DB 테스트 13개와 API 예제 10개가 통과했다. [검색 보고서](../../rag/reports/retrieval-smoke.json)의 FAQ 5개·부서 4개는 기대 대상이 1위였지만 평가 코드의 통과 조건은 **상위 5개 포함**이다. 범위 밖 예제 1개는 `requires_gate` 유지만 확인한다. 실제 범위 밖 판정에 성공했다는 결과가 아니다.

## 추가할 한국어 평가셋

여섯 묶음의 초안 29건은 [`rag/assist_eval_queries.json`](../../rag/assist_eval_queries.json)에 있고, `scripts/응대_평가.py`가 개발셋만 기본 실행한다. [모델 제안서](../../plan/모델_선정과_미세조정_제안.md)의 초기 비교용 **400문항은 제안**이며 아직 검수·작성이 없다. 초안을 400문항 완료로 표시하지 않는다. 초기 모델 평가에 Jev 실행을 요구하지 않는다.

| 묶음 | 반드시 포함할 상황 |
| --- | --- |
| FAQ 적용 | 표현 변형, 오탈자, 서류명, 대상·층수·면적 등의 적용 조건 |
| 조치 요청 | FAQ와 단어가 비슷해도 실제 보수·단속·행정 판단을 요구 |
| 부서 추천 | 구가 다른 같은 이름 과, 본청 업무, 개편 전 부서, 요지 누락 |
| 어려운 비관련 질문 | 청주와 무관한 업무, 유사 단어만 공유하는 질문, 다른 지역 민원 |
| 불확실·복합 | 위치·조건 부족, 두 업무가 섞인 요청, 상충하는 근거 |
| 실패·오용 | 검색/모델 시간 초과, 잘못된 JSON, 가짜 출처·부서, 문서 속 지시문 |

정답은 검색 결과에서 자동 복사하지 않는다. FAQ 현행성·조건과 실제 조치 필요 여부, 부서 업무·관할을 사람이 확인해 라벨을 만든다. 업무 미검증 사례는 정확한 부서 정답이 있는 것처럼 취급하지 않는다. 검토 전 데이터는 별도로 표시한다.

의미가 같은 문장의 표현 변형과 같은 원본에서 만든 사례는 `group_id`로 묶어 개발셋·보류 평가셋 사이에 나누지 않는다. 임계값은 개발셋에서 정하고 보류 평가셋은 최종 비교에 사용한다. 정답 근거가 검색용 지식베이스에 있는 것은 RAG의 목적에 부합하지만, 보류 질문·라벨을 모델 조정에 사용하지 않는다.

검색 회귀 `rag.evaluate`는 Hit@5만 본다. 응대 갈래 칸은 `assist_eval_queries.json`이 쓴다. 검색 순위를 안내 정답으로 복사하지 않는다.

```json
{
  "id": "gate-oos-001",
  "group_id": "foreign-immigration",
  "query": "캐나다 영주권 심사를 청주시에서 해 주나요?",
  "expected_outcome": "human_handoff",
  "acceptable_faq_ids": [],
  "acceptable_department_ids": [],
  "must_not": ["faq_answer", "automatic_transfer"],
  "split": "dev",
  "review_status": "draft"
}
```

## 제안 지표와 통과 기준

| 지표 | 측정 정의 |
| --- | --- |
| 검색 Recall@k | 질문별 관련 정답 문서 중 상위 k개에 회수한 비율. 정답 목록이 불완전하면 Hit@k로 따로 보고 |
| 검색 MRR@k | 첫 관련 문서 순위의 역수 평균; 상위 k개에 없으면 0 |
| 부서 후보 Hit@k | 검증된 허용 부서 중 하나가 후보 상위 k개에 포함된 질문 비율 |
| 오답 자동 안내율 | `faq_answer` 결과 중 근거·적용 조건·내용이 잘못된 건수 / 전체 `faq_answer` 건수 |
| 조치 요청 오안내율 | 실제 조치가 필요한 정답 중 `faq_answer`로 끝낸 건수 / 실제 조치가 필요한 전체 정답 건수 |
| 필수 조건 보존율 | 생성 답변에서 올바르게 표현한 필수 조건 수 / 검수된 정답에서 요구하는 필수 조건 수 |
| 범위 밖 오통과율 | 범위 밖 정답 중 `in_scope`로 통과한 건수 / 전체 범위 밖 정답 건수 |
| 담당자 검토 회수율 | 사람 검토가 필요한 정답 중 실제 `human_handoff` 결과의 비율 |
| 인계 필요 회수율 | 사람 처리가 필요한 정답 중 `department_suggestion` 또는 `human_handoff`로 보낸 비율; 검토 전용 회수율과 구별 |
| 안내·추천 커버리지 | 전체 유효 질문 중 각 결과를 제공한 비율; 오류율과 함께 보고 |
| 지연·실패 | 클라이언트 왕복 시간 p50/p95, 잠금 대기·검색·판정·생성 시간, 시간 초과율 |

분모가 0인 지표는 0% 대신 N/A로 기록한다. 소규모 사례의 비율만으로 운영 성능을 주장하지 않는다. 모델·프롬프트의 목표 수치는 아직 미정이다. 초기 CLI 시연도 출처 없는 답변·가짜 부서·실제 이관 완료 오표시 같은 필수 계약 위반은 테스트에서 허용하지 않는다.

오류율과 안내 비중을 함께 보고 모든 질문을 담당자에게 넘기는 모델이 유리해지지 않게 한다. LLM이 스스로 작성한 confidence를 정답 확률로 사용하지 않는다. 판정용 JSON이 유효하다는 사실과 답변 내용이 정확하다는 사실을 분리해 평가한다.

## 후속 실험의 비교 원칙

- 먼저 추가 학습 없는 LLM + RAG의 모델·프롬프트·검색 설정·평가셋을 고정해 기준 결과를 남긴다.
- Jev 도입은 판정 대체와 추가 검토를 별도 실험으로 구분한다. 검색 근거를 동일하게 전달하고 코드 정책과 결과 계약을 유지한다.
- LoRA는 학습 데이터와 보류 평가의 원문 그룹을 분리하고, 선정 모델의 학습 전/후를 비교한다. 일반 한국어 지시 이행·근거 부족 시 보류 행동의 회귀도 확인한다.
- Jev와 LoRA를 동시에 처음 도입하지 않는다. 한국어 원문 평가를 먼저 하고 Papago는 별도 비교로 남긴다.
- 모델 변경 비교는 저장한 동일 검색 결과를 사용하고, 최종 응대 확인은 실제 검색부터 사용자에게 보이는 결과까지 별도로 평가한다.

실험에는 코드 커밋, 두 원본의 SHA256, 색인 설정, 모델 리비전, 판정 정책/프롬프트 버전, 평가셋 버전, 하드웨어·동시 요청 수·워밍업 조건을 남긴다. 현재 `elapsed_ms`에는 API 잠금 대기 시간이 빠지므로 지연 평가는 호출자에서도 측정한다. 민원 원문·연락처가 포함된 실행 기록은 그대로 Git에 올리지 않으며 공유 보고서에는 합성 입력 또는 비식별 정보만 사용한다.
