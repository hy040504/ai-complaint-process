# 원격 서버 배포와 운영 (navy2025)

[프로젝트 소개](../../README.md) · [서버·API 안내](../../src/README.md) · [네이티브 운영](네이티브_운영.md) · [스크립트 안내](../../scripts/README.md) · [CASE-117](../cases/사례-117-시민·담당자-사이트-분리와-원격-서버-배포-2026-11-21.md) · [CASE-118](../cases/사례-118-무료-외부-공개-Cloudflare-Quick-Tunnel-2026-11-21.md)

Ubuntu 서버에 민원 웹을 올려 쓰는 절차입니다. 개발과 배포는 **`main` 브랜치** 기준입니다. 접속 정보는 저장소에 두지 않고 사용자 PC의 접속용 배치 파일(`navy2025-ssh.bat`)에서만 읽습니다.

## 구성

| 항목 | 내용 |
| --- | --- |
| 위치 | `~/ai-complaint-process` (Git 저장소가 아니라 `git archive` 결과를 풉니다. 배포 커밋은 `.deploy-rev`) |
| Python | `uv`로 설치한 3.12 → `~/.local/bin/python3.12`, 가상환경 `.venv`(검색)·`.venv-web`(웹) |
| DB | 시스템 PostgreSQL 18 + pgvector, `complaints_native` (`complaint_rag`·`complaint_app`), 소켓 peer 인증 |
| 서비스 | systemd **사용자** 서비스 `cheongju-rag`(:8007)·`cheongju-web`(:5000)·`cheongju-lab`(:5010), linger 켜짐 |
| 바인딩 | 모두 `127.0.0.1`. 외부에서는 SSH 터널로만 접근 |
| 시민 / 담당자 | 같은 `:5000` 프로세스의 `/` (시민) · `/staff/` (담당자). 세션 쿠키는 `cj_citizen`·`cj_staff`로 분리 |
| 운영 설정 | `~/.config/cheongju/web.env`(`COMPLAINT_DEMO_LOGIN=0`), 계정 비밀번호는 `~/.config/cheongju/accounts.txt`(권한 600) |

## 배포

```powershell
# 저장소 루트(Windows). main 브랜치의 커밋된 내용을 올립니다.
powershell -File scripts/ops/deploy-remote.ps1
```

1. 이전 배포 목록(`.deploy-manifest`)의 파일만 지웁니다. 가상환경·모델 캐시·업로드·`.env`는 보존됩니다.
2. `git archive main`을 SSH로 전송해 풀고 새 목록·`.deploy-rev`를 기록합니다.
3. `cheongju-rag` → `cheongju-web`·`cheongju-lab` 순으로 재시작하고 헬스·두 화면(`/`, `/staff/`)을 확인합니다.

`-Branch`, `-RemoteDir`, `-SkipRestart`로 조정합니다. 커밋하지 않은 변경은 올라가지 않습니다.

## 최초 설치 (이미 완료)

`setup.sh`가 쓰는 `python3.12`가 apt에 없어 `uv`로 설치했습니다. 설치 순서는 `python3-venv` → `uv` → Python 3.12 → `postgresql-18`·`postgresql-18-pgvector` → `./setup.sh` → `python -m rag ingest`(5,109건, 약 3분) → 사용자 서비스 등록입니다.

## 운영 계정

```bash
# 서버에서. 비밀번호는 인자가 아니라 환경변수 또는 숨김 프롬프트로 받습니다.
cd ~/ai-complaint-process && export PGHOST=/var/run/postgresql PGDATABASE=complaints_native PGUSER=$(id -un)
COMPLAINT_NEW_PASSWORD='새비밀번호8자이상' .venv-web/bin/python -m flask --app src:create_app create-staff --login-id staff_kim --name "김담당" --department "서원구 건설과"
.venv-web/bin/python -m flask --app src:create_app reset-password --login-id staff_admin     # 프롬프트로 입력
.venv-web/bin/python -m flask --app src:create_app deactivate-user --login-id staff_kim
.venv-web/bin/python -m flask --app src:create_app list-users
```

- `--department`를 비우면 전 부서를 다루는 총괄 담당자입니다. 부서는 현행 부서 디렉터리에 있어야 합니다.
- 시연 계정(`citizen-demo`·`staff-demo`)은 변경할 수 없습니다. 비활성 계정은 로그인과 기존 세션이 모두 거부됩니다.
- 시드 계정 비밀번호를 다시 발급하려면 `bash scripts/ops/remote/harden-web.sh --rotate`를 서버에서 실행합니다.

## 접속

서버 포트는 외부에 열려 있지 않습니다. 접속용 배치 파일에 터널 옵션을 붙여 실행합니다.

```bat
navy2025-ssh.bat -N -L 5000:127.0.0.1:5000 -L 5010:127.0.0.1:5010
```

그 뒤 `http://127.0.0.1:5000/`(시민), `http://127.0.0.1:5000/staff/`(담당자), `http://127.0.0.1:5010/`(응대 검사기)로 접속합니다.

## 무료 외부 공개 (Cloudflare Quick Tunnel)

민원 웹(`:5000`)만 `https://무작위.trycloudflare.com`으로 공개합니다. 계정·도메인이 필요 없습니다. 응대 검사기(`:5010`)와 검색 API(`:8007`)는 공개하지 않습니다.

```bash
bash scripts/ops/remote/setup-tunnel.sh      # 최초 설치(cloudflared SHA-256 검증)·서비스 등록·주소 출력. --upgrade 로 재설치
bash scripts/ops/remote/public-url.sh        # 현재 공개 주소·서비스 상태
systemctl --user restart cheongju-tunnel     # 재시작하면 주소가 바뀝니다(비로그인 SSH는 XDG_RUNTIME_DIR 필요)
```

- 공개 주소에서는 시민 `/`와 담당자 `/staff/`, 응대 검사기 단독 페이지 `/lab/`(링크 없음, 담당자 로그인 필요, CASE-128·129)이 열리며, `/design/*`는 항상 `404`이고, `/docs`·`/swagger`·`/openapi*`는 **담당자 로그인(`cj_staff` 서명 쿠키) 없이는 `404`**입니다(`CF-Ray` 헤더 기준). 담당자 콘솔의 `#/staff/api` 화면이 같은 경로를 쓰기 때문에 로그인한 담당자에게는 열립니다(CASE-127). SSH 터널·로컬 접속은 그대로 볼 수 있습니다.
- HTTPS 요청에는 `Secure` 쿠키와 HSTS가 붙습니다.
- 위험: 담당자 사이트도 공개되고(계정 잠금만 보호), 시민 가입·첨부 업로드가 열려 있으며 IP 속도 제한이 없습니다. 주소는 재시작마다 바뀌고 SLA가 없습니다. 자세한 내용은 [CASE-118](../cases/사례-118-무료-외부-공개-Cloudflare-Quick-Tunnel-2026-11-21.md).
- 공개를 끄려면 `systemctl --user disable --now cheongju-tunnel` 입니다.

## 한계

- 응대 검사기 별도 서비스(`:5010`)는 로그인이 없습니다. 터널로만 접근하는 것을 전제로 하며 외부에 노출하지 않습니다. 민원 웹의 `/lab/` 페이지와 `/api/v1/assist*`는 **담당자 로그인이 필요**하고 계정별로 10분에 20회까지 실행할 수 있으며 민원을 저장하지 않습니다(CASE-129).
- LLM 키(`EXAONE_API_KEY` 등)는 서버에 두지 않았습니다. `/health`의 `assistLlm`이 `false`이면 AI 응답은 담당자 검토로 넘어갑니다.
- Swagger 포털(`/docs`)은 사이트 세션이 아니라 기존 단일 쿠키(`session`)를 씁니다.
- 고정 도메인·WAF·IP 속도 제한은 구성하지 않았습니다. 외부 공개는 위 Quick Tunnel(주소가 바뀌는 시연용)만 있습니다.
- 다중 프로세스로 나누면 SSE 이벤트가 프로세스 사이로 전달되지 않습니다(이벤트 브로커 미구현).

## 시연 공통 로그인 `abcd` (2026-11-22)

- 시민 `/`와 담당자 `/staff/` 로그인 화면 모두 아이디 `abcd`와 **서버 환경변수의 시연 비밀번호**로 들어간다(공개 저장소라 값은 문서·코드에 적지 않는다). `users.login_id`가 UNIQUE라 민원인 `abcd`와 담당자 내부 아이디 `abcd@staff`로 저장하고, 로그인 때 사이트가 보내는 `expected_role`로 `<아이디>@<역할>`을 먼저 찾는다. 일반 가입·담당자 생성은 `@`를 막아 선점할 수 없다. 코드는 [`demo_accounts.py`](../../src/complaints/demo_accounts.py).
- 자동 생성하지 않는다. 서버에서 비밀번호 환경변수를 지정해 한 번 실행한다: `COMPLAINT_DEMO_ACCOUNT_PASSWORD=<비밀번호> .venv-web/bin/python -m flask --app src:create_app seed-demo-accounts`(서버는 `~/.config/cheongju/web.env`에 같은 이름으로 두면 된다. 환경변수가 없으면 계정을 만들지 않는다)(반복 실행 가능, 비밀번호·활성 상태를 되돌림).
- **주의:** 담당자 `abcd`는 부서 제한 없는 총괄 권한이고 비밀번호가 약하다. 공개 주소에서는 누구나 담당자 화면(게스트가 낸 민원 포함)을 볼 수 있다. 시연이 끝나면 `deactivate-user --login-id abcd`와 `--login-id abcd@staff`로 끈다.

## 서버 기본 LLM: Codex CLI (2026-11-21)

- 서버(`~/.config/cheongju/web.env`)에 `COMPLAINT_LLM_PROVIDER=codex_cli`, `COMPLAINT_CODEX_COMMAND=<홈>/.local/bin/codex`를 설정했다. Codex CLI는 `npm i -g @openai/codex`(prefix `~/.local/npm`)로 설치하고 `~/.local/bin/codex`에 연결했다(0.171.0). 이 파일은 저장소에 없으므로 `deploy-remote.ps1`이 덮어쓰지 않는다.
- Codex 로그인(`~/.codex/auth.json`)은 서버에 이미 있던 것을 썼다. 만료되면 서버에서 `codex login`을 다시 해야 한다(자격 증명은 저장소·로그에 남기지 않는다).
- 검증: `/api/v1/health`의 `assistLlm=true`, 게스트 접수 후 20초 이내 AI 작업 `succeeded`, 결과 `llm_provider=codex_cli`·`llm_model=gpt-6-luna`. 검증 민원은 삭제했다.
- 한계: 단독 검사기(`cheongju-lab`)의 기본 공급자는 확인·변경하지 않았다. Codex 호출은 약 20초가 걸리고 동시 처리량은 측정하지 않았다.

## 고정 도메인: `cheongju.mib.dpdns.org` (2026-11-22)

- DigitalPlat에서 받은 `mib.dpdns.org`(네임서버 Cloudflare, 같은 GitHub 계정의 `LLMmanager`에서 쓰던 도메인)에 **새 이름 있는 터널 `cheongju-web`**을 만들어 `cheongju.mib.dpdns.org` → `http://127.0.0.1:5000`으로 연결했다. 시민 `/`, 담당자 `/staff/`는 같은 주소의 경로로 구분된다. 기존 터널 7개와 `llm`·`monitor`·`share`·메일(MX/Brevo) 레코드, 와일드카드는 건드리지 않았다.
- 서버: 사용자 서비스 `cheongju-domain-tunnel`(토큰은 `~/.config/cheongju/tunnel.env`, 권한 600, 저장소·로그에 없음). 임시 터널 `cheongju-tunnel`은 중지·해제했다. 재현은 [`setup-named-tunnel.sh`](../../scripts/ops/remote/setup-named-tunnel.sh) `<호스트>`, 현재 주소는 `public-url.sh`.
- 검증: 이 PC에서 `/`·`/staff/`·`/api/v1/health` 200(HSTS·보안 헤더 적용), Swagger·`/docs` 404(공개 시 숨김), 게스트 접수 흐름 9항목 기대값 일치, 검증 민원 삭제.
- 한계: 이 도메인 영역에는 `llm.mib.dpdns.org`(현재 530)도 함께 있다. DigitalPlat 도메인 만료·갱신은 확인하지 못했다. 이름 있는 터널 생성에 쓴 API 토큰은 두 영역(`mib`·`seowon`)에 접근 가능했고 2026-12-31 만료이므로 작업 후 삭제를 권한다.

- 단독 검사기(`cheongju-lab`)도 같은 설정 파일을 읽도록 사용자 서비스 드롭인(`~/.config/systemd/user/cheongju-lab.service.d/env.conf`, `EnvironmentFile=%h/.config/cheongju/web.env`)을 추가했다. 기본 공급자가 `codex_cli`로 해석되고 가용성은 `codex_cli` 사용 가능, `exaone_api`·`openai_api`는 키 없음으로 확인했다(2026-11-22).

## Codex 동시 처리 측정 (2026-11-22)

서버(4코어, 평소 부하 0.2)에서 게스트 민원을 동시에 접수하고 `ai_jobs` 완료까지 잰 결과다(검증 민원은 모두 삭제).

| 시험 | 접수 | 작업 생성 | 전부 완료까지 | 작업별 소요 | 결과 |
| --- | --- | --- | --- | --- | --- |
| 단건 | 1 | 1 | 약 20초 | — | 부서 후보 |
| 동시 4건 | 4 | 4 | 26초 | 16.7~23.0초 | 부서 후보 3·담당자 이관 1, 모두 `codex_cli`/`gpt-6-luna` |
| 동시 8건 | 8 | 6 | 31초 | 14.2~25.5초 | 부서 후보 3·담당자 이관 3, 오류 0 |

- 병렬로 처리되어 4~6건이 동시에 몰려도 단건 소요(약 20초)와 큰 차이가 없었다. 6건 이상의 상한과 장시간 부하는 측정하지 않았다.
- 8건 중 2건은 게스트 접수 제한(`SlidingWindowLimiter` 10건/시간, IP 기준)에 걸려 생성되지 않았다. 앞선 검증이 같은 주소(`127.0.0.1`)의 한도를 썼기 때문이며 설계된 동작이다.
- 같은 민원 문구여도 판정이 `department_suggestion`과 `human_handoff`로 갈렸다. LLM 출력이 비결정적이므로 판정 안정성은 별도 평가가 필요하다.
- 한계: 이 한도는 `ProxyFix(x_for=1)`로 얻은 접속 IP 기준이다. 터널 경유 시 방문자별로 구분되는지는 구조상 그렇다고 판단했을 뿐 실측하지 않았다.
