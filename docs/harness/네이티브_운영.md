# 네이티브 설치·실행·갱신·복구

기준: 2026-10-28 UTC. PostgreSQL 18 + pgvector 0.8.1, Python 3.12 + CPU용 PyTorch를 호스트에서 직접 실행한다. Docker 구성이나 명령 없이 설치·적재·검색·검증한다. 검색 CLI/API까지 구현되어 있으며 LLM 응답·웹·업무 서버는 미구현이다.

## 설치와 DB 초기 준비

Ubuntu 26.04 기준이다. Python 3.12 실행 파일 `python3.12`는 먼저 준비한다. 호스트 기본 Python을 교체하지 않는다.

```bash
sudo apt-get install postgresql-18 postgresql-18-pgvector
scripts/setup-native-python.sh
scripts/setup-native-db.sh
```

`setup-native-db.sh`는 sudo로 로컬 DB 계정·DB·pgvector를 준비한다. 새 DB 계정에는 `LOGIN CREATEDB`를 주며 superuser는 주지 않는다. 기존 계정·DB를 삭제하거나 다시 만들지 않는다. 기존 계정이면 `CREATEDB` 권한 여부를 관리자가 확인한다. 다른 프로젝트 DB와 계정은 수정하지 않는다.

기본 DB 이름은 `complaints_native`, DB 계정은 현재 OS 계정 이름이다. 로컬 소켓 `/var/run/postgresql`의 peer 인증을 사용한다. 기본 포트는 5432이며 이 호스트의 실제 데이터는 `/var/lib/postgresql/18/main`에 저장된다. `.rag-data/postgres`는 이전 환경의 보존 데이터이며 현재 서버에서 사용하지 않는다. `.env`의 이전 비밀번호·포트는 더 이상 읽지 않는다.

현재 서버는 기존 데이터를 복원했으므로 다시 적재할 필요가 없다. **빈 DB를 처음 준비한 환경**에서는 프로젝트 `db/`의 원본·스키마·덤프를 쓴다.

```bash
source scripts/native-env.sh
# 검색 벡터 dump가 있으면 복원. 없으면 스키마만 적용한다.
scripts/restore-rag-dump.sh
# dump가 없을 때만 JSON으로 임베딩을 다시 만든다.
.venv/bin/python -m rag ingest
.venv/bin/python -m rag.verify
```

자료가 있는 컴퓨터에서 다른 컴퓨터로 옮길 dump는 `scripts/export-rag-dump.sh`가 `db/dumps/complaint_rag.dump`에 만든다. 스키마만 적용하려면 `scripts/apply-db-schema.sh`를 사용한다. 원본 JSON과 SQL은 `db/`에 있다.

모델은 `.rag-cache/huggingface`, 임베딩 체크포인트는 `.rag-cache/`에 저장한다. 모델 리비전은 `rag/config.py`에 고정되어 있다. 최초 다운로드에는 네트워크가 필요하며, 현재 transformers 버전은 캐시가 있어도 모델 메타데이터를 조회할 수 있다. 완전 오프라인 실행은 보장하지 않는다.

## 서비스 등록과 시작

```bash
scripts/install-native-service.sh
sudo loginctl enable-linger "$(id -un)"
python3 -m rag status
```

사용자 서비스 `cheongju-rag.service`가 현재 저장소의 절대 경로로 등록된다. linger는 로그아웃 후에도 사용자 서비스를 유지하고 부팅 시 시작하기 위한 설정이다. PostgreSQL은 시스템 서비스로 실행된다. API가 DB보다 먼저 시작해 실패하면 재시작 정책으로 다시 시도한다. `active`만으로 모델 준비가 끝난 것은 아니므로 `/health` 또는 CLI 상태 조회도 확인한다. 이 서버에서는 서비스 재시작 후 준비 완료를 확인했으며 OS 재부팅 자체는 시험하지 않았다.

```bash
systemctl --user status cheongju-rag.service --no-pager
systemctl --user restart cheongju-rag.service
systemctl --user stop cheongju-rag.service
systemctl --user start cheongju-rag.service
journalctl --user -u cheongju-rag.service -n 100 --no-pager
pg_lsclusters
```

서비스 등록 없이 직접 실행하려면 `scripts/native-serve.sh`를 사용한다. 기존 서비스가 실행 중이면 같은 포트로 중복 실행하지 않는다. CPU 실행과 모델 스레드는 `scripts/native-env.sh`에서 지정한다. 서비스 설치 후 실행 경로나 유닛을 바꾸면 설치 스크립트를 재실행하고 서비스를 재시작한다.

## 사용과 공동 작업

`bash rag/test_search.sh`로 상태 확인·FAQ·사례 검색·재정렬·관할 설정을 메뉴에서 실행할 수 있다. 자세한 옵션과 결과 저장 위치는 [검색 테스트 메뉴](../../rag/README.md#검색-테스트-메뉴)를 따른다.

```bash
python3 -m rag status
python3 -m rag search '대형폐기물 배출 방법' --collection faq
python3 -m rag search '711번 버스가 정류장에 서지 않고 지나갔습니다' --collection routing
source scripts/native-env.sh
psql -d "$PGDATABASE"
```

API는 `http://127.0.0.1:8007`, API 문서는 `/docs`, 부서 조회는 `/departments`다. `psql`에서 `\dt complaint_rag.*`, `\d complaint_rag.faq_knowledge`로 테이블·벡터 열을 확인한다. 포트는 외부에 공개하지 않는다. 같은 컴퓨터의 다른 OS 계정에서도 검색 API를 호출할 수 있다. DB를 직접 공동 편집하려면 별도 DB 계정·권한 또는 관리자가 설정한 접근 방식이 필요하다. 현재 계정의 peer 인증이 다른 OS 계정에도 그대로 적용되지는 않는다.

## 테스트와 무결성 대조

```bash
source scripts/native-env.sh
RUN_PG_TESTS=1 .venv/bin/python -m pytest rag/tests -q -p no:cacheprovider
.venv/bin/python -m rag.verify
python3 -m rag.evaluate --output .rag-cache/reports/retrieval-current.json
```

전체 테스트는 `setup-native-db.sh`가 준비한 `complaint_rag_test_template`에서 격리 DB를 생성하고 종료 시 삭제한다. 템플릿에는 pgvector 확장만 있으며 운영 데이터는 없다. `RAG_TEST_TEMPLATE`으로 다른 준비된 템플릿을 지정할 수 있다. 테스트 계정은 DB 생성 권한만 있으면 된다. `RUN_PG_TESTS=1`을 빼면 DB 테스트 3개는 건너뛴다. `rag.evaluate`는 모델 추론이 필요한 별도 검색 회귀이며 자동 답변 정확도를 평가하지 않는다.

## 백업·갱신·복구

변경 전에 원본 JSON·코드 버전·DB 논리 백업을 함께 보관한다. 아래 백업 명령은 매번 새 디렉터리를 만든다.

```bash
source scripts/native-env.sh
umask 077
RAG_BACKUP_DIR=".rag-data/backups/$(date -u +%Y%m%dT%H%M%S)-$$"
mkdir -p "$RAG_BACKUP_DIR"
git rev-parse HEAD > "$RAG_BACKUP_DIR/code-commit.txt"
git diff > "$RAG_BACKUP_DIR/tracked-changes.patch"
cp db/자주_묻는_민원.json db/공개_민원_사례.json "$RAG_BACKUP_DIR/"
pg_dump -Fc > "$RAG_BACKUP_DIR/complaints.dump"
scripts/export-rag-dump.sh
pg_restore --list "$RAG_BACKUP_DIR/complaints.dump" > "$RAG_BACKUP_DIR/archive-list.txt"
```

Git에서 추적하지 않는 파일은 위 diff에 포함되지 않으므로 필요하면 별도 보관한다. 각 명령의 성공을 확인하고 실패한 백업으로 변경을 진행하지 않는다. 자동 주기 백업·외부 보관·보존 기간은 미구성이다. 파일 존재만으로 복원 성공이 보장되지는 않는다.

원본 수집·정규화는 [데이터 사전](../../db/README.md)을 따르며 승인된 데이터 갱신 때만 실행한다. API를 중지하고 백업·원본 변경 검토를 마친 뒤 `.venv/bin/python -m rag ingest`, `.venv/bin/python -m rag.verify`를 실행하고 API를 시작한다. 변경 없는 벡터는 재사용한다. 모델·본문 버전 변경 시에만 `ingest --reembed`를 검토한다. API와 적재 프로세스에 모델을 중복 로드하지 않는다.

복구는 새 임시 DB를 관리자에게 준비받고 확장을 먼저 설치한 뒤 백업을 복원한다. 운영 DB에 `--clean`을 바로 실행하지 않는다. 관리자 소유 확장과 충돌하지 않도록 복원 목록에서 `EXTENSION`과 확장 `COMMENT` 항목을 제외하고 `pg_restore --exit-on-error --no-owner --no-privileges -L 복원목록 -d 복원DB 백업파일`을 사용한다. `PGDATABASE=복원DB .venv/bin/python -m rag.verify`로 같은 버전의 원본과 대조한 뒤 연결을 변경한다. 현재 초기 이전 백업은 `.rag-data/backups/native-migration/complaints.dump`다.

## 장애 확인과 한계

상태 조회 실패 시 사용자 서비스 로그, `pg_lsclusters`, DB 이름·소켓·역할, 모델 캐시 접근 권한을 확인한다. `status --direct`는 DB 조회이므로 모델 준비 여부는 API의 `/health`로 확인한다. 검색 점수는 자동 처리 확률이 아니며 응답은 `retrieval_only=true`, `decision="requires_gate"`를 유지한다.
