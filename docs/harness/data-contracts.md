# 데이터 계약

이 문서는 데이터 변경과 후속 모델 연결에서 지켜야 할 의미를 정의한다. 필드 목록과 수집 명령은 [데이터 사전](../../db/README.md), DB 자료형·제약은 [schema.sql](../../rag/schema.sql)을 따른다.

## 원본과 식별자

| 항목 | 계약 |
| --- | --- |
| FAQ 원본 | `db/자주_묻는_민원.json`: 분야 키와 레코드 배열의 객체 |
| 사례 원본 | `db/공개_민원_사례.json`: 레코드 배열 |
| 문서 키 | `(corpus, source_id)`; `source_id`는 사이트 상세 페이지의 `no` 문자열 |
| 원문 보존 | 원본 레코드를 DB `payload`에 보존하고 검색 결과 `evidence`로 반환 |
| 출처 | `source_url`과 `retrieved_at` 유지. 수집 시각은 정책의 유효성 확인 시각이 아님 |
| 누락값 | 알려지지 않은 값은 정해진 빈 문자열·`null`로 유지. 추측해서 채우지 않음 |

현재 [입력 검사](../../rag/data.py)는 비어 있는 전체 원본, 중복·누락된 `source_id`, 제목·출처·수집 시각 누락, 부서 상태 불일치를 거부한다. 모든 필드의 자료형·URL 소유권·정책 현행성까지 검증하는 완전한 JSON Schema는 아직 없다. 입력 검사를 통과했다는 이유로 안내 내용까지 검증되었다고 보지 않는다.

## 목적에 맞는 검색 본문

| 자료 | 검색에 포함 | 함께 보존하되 같은 용도로 사용하지 않는 정보 |
| --- | --- | --- |
| FAQ | 업무명·분류·본문·대상·접수처 및 조건·처리기간·주의사항 | 변경 전 접수처와 수집 메타데이터 |
| 사례 | 제목·민원 요지 | 과거 처리 답변·부서 표기는 당시 맥락과 부서 검토 자료 |

FAQ의 여러 접수기관·온라인/방문 경로·층수/연면적 조건을 단일 부서명으로 축약하지 않는다. 사례의 요지가 없으면 제목으로 검색하고 `summary_missing=true`로 표시한다. 답변이 없는 사례도 삭제하지 않는다.

8192 모델 토큰을 넘는 임베딩 본문은 현재 적재를 중단한다. 임의 절단 대신 별도 청킹 설계와 평가를 수행해야 한다. 재정렬은 긴 문서를 겹치는 창으로 평가하지만 이는 임베딩 한도를 없애지 않는다.

## 부서 의미와 검증 상태

- `department`: 정규화된 표시 이름. 과거 조직명도 포함할 수 있다.
- `department_original`: 저장 당시 보존한 변경 전 이름. 이미 통일했던 대중교통과의 최초 표기를 복원한 값은 아니다.
- `department_current`: 확인된 현행 부서명. `review_required`이면 반드시 `null`이다.
- `department_checked_on`: 부서 규칙을 확인한 날. 수집기를 다시 실행했다고 자동으로 갱신하지 않는다.
- `department_id`: 명칭 기반 UUID로 만든 내부 키. 정부 기관 코드가 아니며 명칭 변경 시 같은 조직인지 별도 이력 관리가 필요하다.

대중교통과와 건설교통국 대중교통과는 합친다. 흥덕구 건설과와 청원구 건설과처럼 구가 다른 부서는 합치지 않는다. 미래산업과 폐지 사례와 과거 안전정책과 사례는 업무를 개별 대조하며 현재 부서에 일괄 연결하지 않는다.

`routing_eligible`은 해당 사례에 현재 부서 식별자가 있다는 의미다. `duty_status`, `jurisdiction_status`, `automatic_routing_ready`는 별도다. 현재 부서 이름으로 추출한 구 정보만으로 실제 업무 관할을 확정할 수 없다. API의 `automatic_transfer=false`도 유지한다.

재적재는 **동일 내부 ID로 남아 있는 부서**의 보완된 업무분장·관할 검증 값을 보존한다. 원본에서 사라지거나 이름 변경으로 ID가 달라진 부서는 삭제·신규 생성될 수 있으므로 이전 검증 정보를 별도 백업하고 이관해야 한다.

## 갱신 시 남길 근거

변경 전후 원본 SHA256, 건수, 추가·삭제 `source_id`, 부서 매핑 변경, 원문 확인 근거를 기록한다. DB 적재 후에는 [무결성 검사와 검색 회귀](evaluation.md)를 수행한다. 데이터만 바뀐 것인지 본문 구성·모델·토큰화가 바뀐 것인지 구분해 재색인 범위를 결정한다.

향후 FAQ 승인 기록에는 `(corpus, source_id, content_hash)`, 확인 항목·출처·시각·상태를 저장하는 방식을 권장한다. 이는 **추가 설계 항목**이며 현재 JSON이나 DB에 구현된 필드가 아니다. 원문 내용이 바뀌면 기존 승인도 다시 검토할 수 있어야 한다.

## 시연 웹의 민원·대화 데이터: 후속 설계

시연 웹은 게시판과 민원 작성·답변 교환 서버를 구현할 계획이다. 다음은 미구현 업무 데이터 계약 제안이며 현재 `complaint_rag` 테이블에 이미 추가된 필드가 아니다.

- 서버에서 발급할 `complaint_id`와 수집 자료의 `(corpus, source_id)`를 구별한다.
- 민원 본문·대화·작성 역할·공개 범위·처리 상태·변경 이력을 업무 데이터로 저장한다. AI 검토에는 대상 입력 버전·근거·후보 부서·모델/정책 버전과 성공·실패를 연결한다.
- 게시글·시민 추가 문의·담당자 답변을 원본 JSON·벡터 색인·학습 데이터에 자동 반영하지 않는다.
- AI 결과가 민원 본문보다 늦게 도착하거나 실패해도 글을 유실·중복 생성하지 않도록 저장과 검토 상태를 분리한다.
- 목록·상세·답변·상태 변경은 서버의 역할·조회 범위를 검사한다. 일반 시민에게 검색 API의 원본 payload 전체를 그대로 전달하는 구조로 확대하지 않는다.
- 시연 서비스의 민원 ID·등록·답변 상태와 청주시 공식 접수번호·행정 이관 상태를 분리한다.

저장 모델·API·업무 상태의 구체적인 명칭은 [웹·민원 서버 구현계획](../../plan/시연_웹_게시판과_민원_서버_구현계획.md)의 제안에서 구현 시 확정한다.

2026-10-27 [통합 상세설계](../../plan/민원_웹_MVP_상세설계와_분야별_작업계획.md)는 다음 계약을 추가 제안한다. 아직 업무 테이블은 생성하지 않았다.

- 민원 업무 상태, AI 작업 상태·단계, 답변 게시 상태를 분리한다. AI 완료가 게시·민원 해결 완료를 뜻하지 않는다.
- AI 원본과 편집 버전을 보존한다. `origin`, 기원 작업, 편집자·게시자·사유를 구분하고 배지는 서버 데이터에서 결정한다.
- 민원 본문·추가 문의·삭제·담당자 게시가 바뀌면 입력 맥락 버전을 갱신한다. 늦은 작업은 기록만 남기고 현재 게시본에 적용하지 않는다.
- 민원과 최초 작업, 작업 상태와 이벤트를 각각 원자적으로 저장한다. 이벤트는 저장 이후 전송하며 재수신·재시도에 중복 반영하지 않는다.
- 담당자 초안·시스템 프롬프트·내부 추론을 시민 응답·이벤트에 포함하지 않는다. 논리 삭제와 답변 철회는 이력·권한·복구 규칙을 함께 갖춘다.
